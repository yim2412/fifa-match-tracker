## 버전 규칙

`a.b.c` — **a** 큰 패치(구조가 바뀌어 새로 익혀야 함: 메뉴 재편 · 저장 형식 큰 변경) · **b** 중간(새 기능·화면) ·
**c** 작은 수정(버그·문구·작은 성능). 섞이면 큰 쪽을 올리고 **아래 자리는 1로** 돌린다(1.4.2 → 2.1.1).
예외: 공개판 1.0.2 의 가운데가 0 이라 창 크기 수정만 1.0.3, 다음 기능 패치(1.1.1)부터 새 규칙.
`updatecheck` 는 세 자리 숫자 비교라 이 체계에서 그대로 동작한다.

## 모든 버전 공통 — 끝났다고 보는 기준

1. 새 코드마다 테스트 + **일부러 되돌린 변이가 FAIL** 하는지(`mutate.js` 또는 손 변이). 커밋 메시지에 "변이 N건 FAIL".
2. 테스트 7종 통과 · CI 초록 · `check_api.py` 에 새 출처마다 한 줄.
3. 1만 경기 계정으로 **검색→첫 화면 · 메뉴 전환 시간**을 이전 값과 비교(지금: 마지막 계정 약 1.3초, 메뉴 0.3초 이하).
4. 창 1280×720(1.0.3 뒤로는 작은 화면 최소 높이 포함)에서 잘림 없음 — 기존 offscreen 테스트.
5. exe 빌드 → 2번 모니터 스모크(창을 띄워야 할 때) · 크래시 로그 증가 0.
6. `CHANGELOG.md` 절 · README · 프로젝트 `CLAUDE.md` 파일 표 갱신 → `release.py` → 공개 명령은 사용자.
7. 홈페이지(데이터센터)를 새로 읽는 기능은 전부 `config.WEB_DATA` 뒤 + `test_web_data_switch_blocks_every_request` 에 등록.
   이용 안내 문구가 실질적으로 바뀌면 `NOTICE_VERSION` 을 올린다.
8. 화면이 쓰는 새 분석 함수는 `core_api.py` 의 import 와 `__all__` 에 한 줄(19단계 경계 — 안 하면 경계 테스트가 FAIL).
   지우는 함수는 거기서도 뺀다.

9. **2회차는 1회차 [상]을 반영한 줄 + 그 줄이 닿는 진입점 표 행만** — `python tools/review_kit.py diff <앞 회차 커밋> --bundle`: 바뀐 줄을 절별로, 바뀐 이름을 품은 **안 바뀐** 진입점 표 행, 바뀐 줄의 이름만으로 만든 묶음까지 한 파일. 그래서 회차마다 계획을 커밋해 둔다(커밋이 회차 경계). 끝내는 조건의 "마지막 회차는 계획 전체"는 검토자 1명만.
10. **다른 회사 모델 — 무료 Gemini 는 돌아다니는 검토자로 못 쓴다**(2026-10-05 실측). 구글 계정 로그인 무료 등급은 Gemini CLI 지원이 끊겼고(`IneligibleTierError` — Antigravity 로 옮기라 함),

## 배포 보호 준비 (2026-10-05 사용자와 결정 — 19단계 끝 · 20~22단계는 나중)

**목표**: 기능이 거의 완성되면 핵심 알고리즘을 쉽게 베끼지 못하게 배포한다. **지금은 개발 편의 우선** — Nuitka·난독화·보호 빌드는 적용하지 않는다.

**정한 것**
- **저장소는 공개 유지(MIT).** 비공개 전환은 기각 — 기존 설치자의 자동 업데이트(`config.LATEST_RELEASE_API`)·릴리스 링크·`.iss` URL·UA 의 주소가
  전부 끊기고, 이미 공개된 커밋의 MIT 허락은 회수되지 않는다.
- **핵심만 가린다** — 그때 가치 있는 알고리즘(예측 등)만 비공개 저장소로, 공개 저장소엔 약속(`core_api`)과 간이 대체만. 배포판엔 **Nuitka 로
  컴파일한 `.pyd`**. 이미 공개된 `analysis.py`·`stats.py` 는 못 가린다 — 가려지는 건 분리 뒤 새로 만들거나 크게 바꾼 것부터.
- **PySide6 전환이 선행 조건** — PyQt6 는 GPL v3 라 숨긴 모듈을 묶은 exe 를 배포하면 위반이다(LGPL 인 PySide6 는 Qt DLL 을 바꿔 끼울 수 있게만 두면 된다).
- **암호화(PyArmor 류)는 안 쓴다** — 실행 때 어차피 풀리고, 모르는 사람에게 주는 exe 라 백신 오탐이 치명적. 컴파일만으로 원문 복원 도구가 안 통한다.
  결과를 보고 공식을 추정하는 것·기계어 분석은 어떤 방법으로도 못 막는다(완전히 막으려면 서버 — 지금 규모엔 과함).
  **기대치**: "파일을 AI 에 던져 원문 받기"는 막지만, Nuitka 는 속성 이름·문자열·상수가 바이너리에 남고 흐름이 C API 호출 나열이라
  디스어셈블러 + AI 로 시간을 들이면 이 규모의 통계 공식은 대부분 되살아난다고 본다. 정말 지킬 알고리즘이 생기면 그것만 서버로 — 그때 다시 판단.
- **카카오톡 봇은 완전히 안 한다**(사용자) → 19단계에서 지웠다(`cf8491d`).

**19단계 ✅ 끝(2026-10-05, 1.2.1 에 실림 · 기능 변경 없음)** — 봇 삭제 · 화면 ↔ 분석 경계 `core_api.py` · 저장소 주소 한 곳(`config.REPO_SLUG` · `.iss` 의 `RepoUrl`).
**6~18단계의 새 분석 코드는 `core_api` 를 거친다**(화면 파일이 analysis·stats·models 를 직접 import 하면 `test_ui_reaches_analysis_only_through_core_api` 가 FAIL).

**Nuitka 위험 점검(19단계 보고 · 코드는 안 고침)** — 보호 빌드를 시작할 때 이 표부터. 근거: 코드 = 2026-10-05 코드 확인 · 인용 = 기억/문서, **실측 전엔 믿지 않는다**.

### B 카드 정보 캐시 (15단계 — 공용 부품 전체)

- **표를 나눈다**(R7 — 값마다 바뀌는 단위가 다르다): `card_info(spid PRIMARY KEY, name, position, base_ovr, salary, fetched_on)` — 카드 하나에 하나 ·
  시세는 이미 있는 `card_prices(spid, grade)`(하루). 개요의 `card_info(spid, grade, price, salary, ovr, …)` 한 표는 **급여가 강화마다 복사되고 OVR 은 강화·포지션마다 달라** 한 페이지로 못 채운다.
- **강화별 OVR** = `base_ovr` + `config.GRADE_OVR_BONUS[grade]`(1~13). 표 값은 15단계 첫 줄에 능력치 시뮬레이터(`playerinfo.fetch_ability_sim` — PC PlayerAbility POST)로
  카드 셋 × 1~13강을 재서 정한다 → `check_api.py` 에 한 줄(표가 넥슨과 어긋나면 [FAIL]). 칩·표의 OVR 은 **카드 기본 포지션 기준**이라고 툴팁에 쓴다(다른 자리에 세우면 게임 값과 다르다).
- **채우기**: `fetch_player_info` 가 한 요청으로 시세·급여·OVR 을 같이 읽는다(본 카드 구역 앵커 — R7). `card_info` 는 30일 TTL(라이브 패치로 바뀔 수 있다 — 30일인 근거는 없다: 구현 뒤 TTL 지난 카드의 값이 바뀐 비율을 `check_api` 줄로 본다 → 재지 않은 것).
  하루 시도 상한은 기존 `PRICE_FETCH_MAX`(80 — 시도 수)와 **같은 계수기**를 쓴다(카드 상세 요청이 같은 요청이라).
  **집계에는 카드 상세가 필요 없다** — 랭커 픽·12 의 카드 이름은 메타 `spid`(8만 건대 — nexon_api.py:24 주석)로. 요청은 **화면에 띄운 축구장의 칩**(최대 11장 × 띄운 수)만.
- 개요의 "출처 둘(선수 페이지 · 팀컬러 선수 JSON)" 중 팀컬러 선수 JSON 은 **2.2.1(7)의 새 요청**이라 2.1.1 엔 선수 페이지 하나. 2.2.1 이 붙인다.
- `WEB_DATA` 꺼짐 → 시세·급여·OVR 칸만 비운다(이름·포지션·강화는 경기 상세·메타).

### 12 선수 색인 · 선수로 구단주 찾기 (16단계)

- **표**(R2 — 정수 키, R12 — rowid 를 안 쓴다): `squad_owner(id INTEGER PRIMARY KEY, ouid TEXT UNIQUE, nickname TEXT, last_day INTEGER)` ·
  `squad_match(id INTEGER PRIMARY KEY, match_id TEXT UNIQUE)` · `match_squads(spid, day, match, owner, po, grade, PRIMARY KEY(spid, day, match, owner, po)) WITHOUT ROWID` — 선발만(28 제외).

  백필은 검색·로더가 없을 때만, 낮은 스레드 우선순위(`rankcollect` 와 같은 ctypes — 핸들 형 주의). 1만 경기 첫 화면 시간(공통 기준 3)에 백필이 끼면 안 된다 — 첫 화면 뒤 30초부터.
- **찾기 화면**: 선수 이름(메타 `spid` 8만 건 — 입력 2글자부터 후보) + 카드 시즌(`stats.season_id_of`) + 강화(선택) + 팀컬러(선택) → 그 카드를 **최근 30일**(`config.CARD_OWNER_DAYS`) 선발로 쓴 구단주 목록
  (닉네임 · 마지막 사용일 · 횟수 · 포지션 · 팀컬러 · 순위). 팀컬러·순위는 **마지막 스냅숏 1만 명 안이거나 `team_colors` 캐시에 있을 때만** — 없으면 "모름"(필터를 걸면 빠진다고 화면에 적는다).
  범위: 내 DB 구단주(검색한 계정 + 그 상대 — R1 11,902명) + 랭커 픽 200(6이 `matches` 에 넣은 경기). 누르면 그 구단주 검색.

### 6 랭커 픽 (16단계) — 상위 200

- **대상**: 마지막 스냅숏 1~200위. 스냅숏이 없으면(수집 꺼짐 · 첫 회차 전) 화면은 "랭킹 수집을 켜면 하루 뒤부터" — 팀컬러 목록(`RankListLoader`)이 남긴 스냅숏도 스냅숏이다.
- **요청 0 으로 되는 것**(R3): 팀컬러·포메이션 분포 — 스냅숏 행.
- **요청이 드는 것**(R6): 선발 카드·강화 — `RankerPickLoader`(작업 스레드 · 자기 연결 · `cancel()` · 요청 번호). 랭커마다 ouid(`ranker_squads.ouid` 캐시 — 닉네임이 바뀌면 다시) → 최근 경기 1 → 상세(이미 `matches` 에 있으면 0요청).
  상세는 `matches` + `match_players`(그 랭커 ouid 만)에 저장 — 12 색인이 같이 잡는다. **`accounts` 에는 넣지 않는다**(R11).
  `ranker_squads(profile_sn PRIMARY KEY, nickname, ouid, match_id, match_day, fetched_at)` — 오래된 것부터, 하루 **`config.RANKER_PICK_DAILY_REQ`(U2 300)** 안에서. 상한은 요청 **시도** 수(실패도 센다).
- **언제**: 랭킹 수집 회차 끝(`rankcollect` 의 회차 끝 훅 — `sync_tracked_elo` 옆) **그리고** 앱이 한가할 때 — 오픈API 를 쓰는 다른 로더(검색 · 구단주 비교 · 거래 받기)가 돌면 랭커마다 사이에서 멈추고 양보(`TradeLoader` 와 같은 규칙).
  **오픈API 백그라운드 로더는 한 번에 하나**: 거래 → 랭커 픽 순. 429 를 받으면 그날 멈춘다(키 입력 창으로 보내지 않는다 — `quota_hit` 아님).
- **화면**: [픽] 팀컬러·포메이션 비율 · 포지션 줄별 많이 쓴 카드(강화 분포 막대) · 받은 랭커 수 "200명 중 N명(마지막 받은 날)" · 표본 흐림 규칙(1.2.1) 그대로.
  "내 스쿼드 vs 랭커" — 내 최근 경기 선발을 v2 축구장에, 칩마다 그 카드의 랭커 픽률(같은 줄). [추천] 탭은 17단계.

### 11-lite 랭커 기반 추천 (17단계)
