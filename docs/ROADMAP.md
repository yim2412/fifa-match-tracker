## 버전 규칙

`a.b.c` — **a** 큰 패치(구조가 바뀌어 새로 익혀야 함: 메뉴 재편 · 저장 형식 큰 변경) · **b** 중간(새 기능·화면) ·
**c** 작은 수정(버그·문구·작은 성능). 섞이면 큰 쪽을 올리고 **아래 자리는 1로** 돌린다(1.4.2 → 2.1.1).
예외: 공개판 1.0.2 의 가운데가 0 이라 창 크기 수정만 1.0.3, 다음 기능 패치(1.1.1)부터 새 규칙.
`updatecheck` 는 세 자리 숫자 비교라 이 체계에서 그대로 동작한다.

## 모든 버전 공통 — 끝났다고 보는 기준

1. 새 코드마다 테스트 + **일부러 되돌린 변이가 FAIL** 하는지(`mutate.js` 또는 손 변이). 커밋 메시지에 "변이 N건 FAIL".
2. 테스트 7종 통과 · CI 초록 · `check_api.py` 에 새 출처마다 한 줄.
3. 1만 경기 계정으로 **검색→첫 화면 · 메뉴 전환 시간**을 이전 값과 비교(지금: 마지막 계정 약 1.3초, 메뉴 0.3초 이하).
4. 창 1280×720(1.0.3 뒤로는 작은 화면 최소 높이 포함)에서 잘림 없음 — 기존 offscreen 테스트.
5. exe 빌드 → 2번 모니터 스모크(창을 띄워야 할 때) · 크래시 로그 증가 0.
6. `CHANGELOG.md` 절 · README · 프로젝트 `CLAUDE.md` 파일 표 갱신 → `release.py` → 공개 명령은 사용자.
7. 홈페이지(데이터센터)를 새로 읽는 기능은 전부 `config.WEB_DATA` 뒤 + `test_web_data_switch_blocks_every_request` 에 등록.
   이용 안내 문구가 실질적으로 바뀌면 `NOTICE_VERSION` 을 올린다.
8. 화면이 쓰는 새 분석 함수는 `core_api.py` 의 import 와 `__all__` 에 한 줄(19단계 경계 — 안 하면 경계 테스트가 FAIL).
   지우는 함수는 거기서도 뺀다.

**독립 검토자가 새 [상] 결함 0개**(새 [중]·[하]는 계획에 적고 구현 때 테스트로 잡는다) · 보고에 **"재지 않은 것"** 목록을 붙인다.

**검토를 돌리는 방법 — 토큰 아끼기**(2026-10-04 사용자: "토큰 사용이 너무 심하다" → 아래 여섯 가지로). 실측: 검토자 1명이 회당
13만~19만 토큰, 1.1.1 은 2명 × 4회차로 100만 넘게 들었다 — 대부분 큰 파일(`app_main.py` 약 4,800줄)을 매번 처음부터 읽는 데 썼다.
1. **계획이 끝나면 새 세션에서 구현** — 긴 세션은 답할 때마다 쌓인 맥락 전체를 다시 읽는다. 정본은 이 문서라 새 세션은 여기만 읽고 시작한다.
2. **다음 회차는 같은 검토자를 이어 쓴다**(SendMessage) — 이미 읽은 코드를 다시 안 읽는다. "이 줄들이 바뀌었으니 거기만"으로 시킨다.
3. **보고는 짧게** — [상]·[중]만, 결함마다 한 줄 근거, "확인한 것" 목록 없이.
4. **이미 잰 사실은 장부로 넘긴다** — 계획 머리말의 실측값은 다시 재지 말라고 적어 준다(넥슨 요청 속도·DB 내용을 매 회 다시 쟀다).
5. **계획은 고칠 곳만 고친다** — 절 전체를 새로 쓰지 않는다(4차에 20군데 교체로 바꿨다).
6. **[중]·[하]는 구현하면서 테스트로** — 최근 회차 결함 대부분이 "구현 뒤 실측"·테스트로 바로 잡힐 성격이었다. 그래서 끝내는 조건이 [상] 0개다.

**더 줄이기(2026-10-05 사용자: "추천대로")** — 1.3.1 검토 1회차 실측: 검토자 B 14만 토큰.
7. **단계 위험도로 검토자 수를 나눈다** — 기존 데이터로 화면만 그리는 단계(예: 1.3.1 의 8단계)는 1명, 새 데이터 길·저장 형식·모델(9·10단계)은 2명. ⑫ "2명 이상"의 예외.
8. **코드 관점 검토자에게는 근거 묶음을 준다** — 계획이 닿는 코드 조각(줄 번호 포함)을 파일 하나로 뽑아 주고, grep 은 의심 가는 결함 확인에만. 제 사각지대가 옮겨 가지 않게 **다른 검토자는 묶음 없이** 자유롭게 찾는다.
9. **2회차는 1회차 [상]을 반영한 줄 + 그 줄이 닿는 진입점 표 행만.** 끝내는 조건의 "마지막 회차는 계획 전체"는 검토자 1명만.
10. **다른 회사 모델 — 무료 Gemini 는 돌아다니는 검토자로 못 쓴다**(2026-10-05 실측). 구글 계정 로그인 무료 등급은 Gemini CLI 지원이 끊겼고(`IneligibleTierError` — Antigravity 로 옮기라 함),

   남은 쓸모: 8번의 근거 묶음을 **요청 한 번**에 넣는 단발 검토(하루 한두 번) — 묶음 밖은 못 보니 독립성이 약하다. 지적은 그대로 믿지 않고 코드로 확인한다. 저장소는 공개라 코드는 보내도 되지만 `fifa.db`·`.env`·`rank.db` 내용은 보내지 않는다.

## 배포 보호 준비 (2026-10-05 사용자와 결정 — 19단계 끝 · 20~22단계는 나중)

**목표**: 기능이 거의 완성되면 핵심 알고리즘을 쉽게 베끼지 못하게 배포한다. **지금은 개발 편의 우선** — Nuitka·난독화·보호 빌드는 적용하지 않는다.

**정한 것**
- **저장소는 공개 유지(MIT).** 비공개 전환은 기각 — 기존 설치자의 자동 업데이트(`config.LATEST_RELEASE_API`)·릴리스 링크·`.iss` URL·UA 의 주소가
  전부 끊기고, 이미 공개된 커밋의 MIT 허락은 회수되지 않는다.
- **핵심만 가린다** — 그때 가치 있는 알고리즘(예측 등)만 비공개 저장소로, 공개 저장소엔 약속(`core_api`)과 간이 대체만. 배포판엔 **Nuitka 로
  컴파일한 `.pyd`**. 이미 공개된 `analysis.py`·`stats.py` 는 못 가린다 — 가려지는 건 분리 뒤 새로 만들거나 크게 바꾼 것부터.
- **PySide6 전환이 선행 조건** — PyQt6 는 GPL v3 라 숨긴 모듈을 묶은 exe 를 배포하면 위반이다(LGPL 인 PySide6 는 Qt DLL 을 바꿔 끼울 수 있게만 두면 된다).
- **암호화(PyArmor 류)는 안 쓴다** — 실행 때 어차피 풀리고, 모르는 사람에게 주는 exe 라 백신 오탐이 치명적. 컴파일만으로 원문 복원 도구가 안 통한다.
  결과를 보고 공식을 추정하는 것·기계어 분석은 어떤 방법으로도 못 막는다(완전히 막으려면 서버 — 지금 규모엔 과함).
  **기대치**: "파일을 AI 에 던져 원문 받기"는 막지만, Nuitka 는 속성 이름·문자열·상수가 바이너리에 남고 흐름이 C API 호출 나열이라
  디스어셈블러 + AI 로 시간을 들이면 이 규모의 통계 공식은 대부분 되살아난다고 본다. 정말 지킬 알고리즘이 생기면 그것만 서버로 — 그때 다시 판단.
- **카카오톡 봇은 완전히 안 한다**(사용자) → 19단계에서 지웠다(`cf8491d`).

**19단계 ✅ 끝(2026-10-05, 1.2.1 에 실림 · 기능 변경 없음)** — 봇 삭제 · 화면 ↔ 분석 경계 `core_api.py` · 저장소 주소 한 곳(`config.REPO_SLUG` · `.iss` 의 `RepoUrl`).
**6~18단계의 새 분석 코드는 `core_api` 를 거친다**(화면 파일이 analysis·stats·models 를 직접 import 하면 `test_ui_reaches_analysis_only_through_core_api` 가 FAIL).

**Nuitka 위험 점검(19단계 보고 · 코드는 안 고침)** — 보호 빌드를 시작할 때 이 표부터. 근거: 코드 = 2026-10-05 코드 확인 · 인용 = 기억/문서, **실측 전엔 믿지 않는다**.

- **옵션은 전부 `set_data` 인자**(생성자는 지금 그대로 — 검토 A): `set_data(points, *, axis=PCT_AXIS, avg=True, baseline=None, ma=None, counts=False, ref_series=(), x_dates=None)`.

  - `baseline`: 축 눈금과 같은 값이면(50) **그 격자선을 진하게** 그릴 뿐 글자를 따로 안 쓴다(축 글자와 겹침 — 검토 A). 눈금 밖 값이면 점선 + 글자, 글자 칸 충돌 규칙(charts.py:193-197)에 넣는다.

  - `counts`: 아래 띠(그래프 높이의 18%, 최소 24px)에 점마다 경기 수 막대 + 가장 큰 값만 숫자. 축 글자 칸 위에 놓는다.

### ② 흐름 분석 — 결과 띠 · 근거 막대 (9단계)

- 테스트(`test_analysis`): basis 를 채우는 규칙마다 손 데이터로 값 대조 · 문장이 나온 basis 는 `n ≥ min_n`. 변이: 한 규칙에서 basis 를 빼면 → 전수 표 테스트 FAIL(규칙 이름 목록과 대조).

| 위 넷 중 `EloLoader` 를 띄우는 세 경우 **전부** | `EloLoader` 끝 → `PredictWorker(ouid)`(10단계) | 작업 스레드 | `test_predict_runs_on_every_open_path` |

- `EloLoader` 는 `fifa.db`(`elo_history` — 인덱스 `(ouid, taken_at)`)와 `rank.db cut_elo` 를 읽어 `elo_ready(ouid, object)`(`pyqtSignal(object)` — PyQt 규칙 8).
  `rank.db` 는 **없으면 만들지 않고 읽기 전용으로**(`rankcollect.open_rank_db_ro(path) -> Connection | None` — `read_status` 와 같은 이유: 수집을 켠 적 없는 사람에게 파일이 생기지 않게, 검토 A 10) ·
  읽고 바로 닫는다(열린 연결이 `delete_db` 를 막지 않게).
- **늦게 끝난 읽기가 새 값을 덮지 않게**(검토 A 2-1): 창이 `EloLoader` 를 띄울 때마다 요청 번호를 올리고, `elo_ready` 는 **그 계정의 마지막 요청 번호**일 때만 받는다(`PredictWorker` 도 같은 규칙).
  `test_elo_includes_this_search_point` 는 **먼저 띄운 로더가 나중에 끝나게** 순서를 고정한다(변이: 번호 검사 제거 → FAIL).
- **종료 정리**(검토 A 2-2 — 프로젝트 CLAUDE.md tray 행 "새 종료 경로는 여기를"): `EloLoader`·`PredictWorker` 를 `MainWindow.shutdown(fast)` 의 정리 목록에 — `cancel()` → `wait()`(fast 면 합계 1초 규칙 안). 테스트 `test_shutdown_stops_elo_and_predict_workers`.
- **`elo_saved` 를 내는 자리**(검토 A 2-7): `_save_elo` 안에서 `store.save_elo` 가 **True(새 줄을 적음)일 때만**, 그리고 `self._cancel` 이 아닐 때만(`rank_ready` 와 같은 규칙). 같은 값이라 안 적었거나 실패면 안 낸다.
- 창은 `self._elo: dict[ouid, EloSeries]` — 다른 계정 값은 그 칸에만 · 같은 계정 None 이면 보던 값 · **그리는 건 늘 `self._ouid` 칸**(계정을 바꿨는데 이전 그래프가 남지 않게 — 검토 A 12).
  `_render_trend` 가 매번 이 dict 로 다시 그린다(가볍다 — 읽기는 신호 때만). `release_memory` 는 비우지 않는다(작다 — 1.2.1 `_max_division` 과 같은 규칙).
- 테스트: `sync_tracked_elo` 멱등 · 따라가기 목록의 프로필 번호만 · `prune_raw` 뒤에도 elo_history 는 남음 · fifa.db 잠김이면 회차 성공 · 따라가기에 넣은 계정이 다음 회차에 14일치(검색만 한 계정은 스냅숏 줄 없음) ·

### 9 시즌 말 순위 예측 — `predict.py` (10단계)

> 1회차 검토 뒤 다시 썼다(2026-10-05) — 첫 안(결과당 점수 회귀 + 최근 승률 고정)은 **점수가 오르면 승률이 내려가는 되돌림이 없어** 하루 100판 × 30일이면 수천 점이 한 방향으로
> 쌓이고 확률이 0/1 로 붙었다(검토 B 1). 범위가 좁게 나오고(B 2) · 순위 구간이 넓어 계수가 사용자 자리와 안 맞고(B 3) · 1만 위 밖으로 떨어진 사람이 빠져 치우쳤다(B 4).
> **새 안: 같은 점수대 실제 구단주들의 하루 ELO 변화를 뽑아 이어 붙인다** — 되돌림·승률 흔들림·연속성이 데이터에 그대로 들어 있다.

**무엇을 내나**: "지금 흐름이 이어지면 — 200위 안 N% · 1,000위 안 M% · 예상 순위 80% 범위 a~b위 · 가정: 시즌 종료 10/29~11/19(중앙 11/12, 추정) | 11/12(공지)".
확률은 `<1%`·`>99%` 로 끝을 막는다. 숫자를 못 내면 **원인별 문구**(아래 표). 화면 어디에도 "보정"이라는 말을 쓰지 않는다(데이터 양 조건일 뿐 — 검토 B 18).
목표는 `config.RANK_TIERS` 의 앞 둘(200 · 1,000 — 앱이 이미 쓰는 구간)로 근거를 바꿨다("최상위 보상 구간"은 장부에 근거가 없었다 — 검토 B 7). 1만 위 컷은 시즌 길이에 따라 크게 움직여(R4) 목표로 안 쓴다.

**하루 걸음 표본** `predict.day_steps(rank_conn) -> Steps` — 원본이 남은 14일의 스냅숏 중 **간격 20~28시간이고 `season_seq` 가 같은** 이웃 쌍(검토 B 19 · A 14: 같은 날 두 번 찍힌 쌍 · 시즌 경계 쌍 제외)마다,
두 번 다 있는 구단주의 (시작 ELO, ΔELO, Δ경기 = Δ(승+무+패)) — 프로필 번호로 잇는다. 두 번째에 없는 구단주(1만 위 밖으로 떨어짐)는 **점수대별 이탈 수**로만 센다.
- **멈춤 지점(구현 첫 일)**: 원본의 승·무·패가 **시즌 누적**인지 실측 — 두 스냅숏 사이 Δ(승+무+패)가 그 사이 경기 수와 같은 차수인지 · 새 시즌에 0 으로 돌아가는지. 아니면 Δ경기를 못 써서
  이 설계가 무너진다 → 계획을 고치고 다시 검토.
- 원본 14일만 쓰므로 **새 영구 표가 없다**(첫 안의 `elo_fit` 은 뺐다) — 개인정보 약속(원본 14일)과 같다. 걸음을 따로 쌓지 않는다.

**시뮬레이션** `simulate(state, steps, cuts, end_days, rng, n=PREDICT_RUNS)` — 경로마다:
1. 종료일 하나를 뽑는다(아래). 남은 날 수 = 종료일 − 오늘.
2. 날마다 내 경기 수 g 를 **내 최근 14일 하루 경기 수**(저장된 경기 — 쉬는 날 0 포함 · 몰수·"오류" 경기도 넥슨 ELO 에 들어가므로 센다, 검토 B 17)에서 뽑는다.
   14일은 **마지막으로 받은 경기 날짜까지**로 센다 — 트레이에 있는 동안(검색 없이) 수집 끝에 돌면 그 뒤 날이 "경기 0"으로 들어가 줄어든다(검토 B 2-9).
3. g = 0 이면 그대로. 아니면 **지금 경로 ELO ±`PREDICT_ELO_BAND`(50) 안에서 출발했고 그날 경기 수가 g 와 같은 칸**인 걸음 하나를 뽑아 더한다.
   칸 경계는 구현 첫 일에 걸음 표본의 하루 경기 수 분포 **4분위**로 정한다(R6 처럼 하루 100판 안팎이 흔해 고정 "61+" 는 61판과 200판을 한 칸에 넣는다 — 검토 B 2-6). 정한 값은 장부에.
   **3일 묶음**(같은 구단주의 이어진 사흘 — 연승·연패 연속성): 첫날만 g 칸을 맞추고 묶음의 나머지 이틀은 **그 구단주의 경기 수 그대로** 쓴다(내 경기 수 뽑기를 그 이틀은 건너뜀 — 검토 B 2-4).
   묶음 수가 칸마다 `PREDICT_MIN_BLOCKS`(50) 미만이면 하루씩. 묶음이 몇 개 나오는지는 구현 첫 일 실측(장부).
   **칸이 비면**(경로 ELO 가 표본 최고점 위로 — 검토 B 2-5): 띠를 ±100 · ±200 으로 넓히고, 그래도 없으면 그 경로는 그날 0(오르지 않음 — 표본 밖으로 밀어 올리지 않는다). 넓힌 경로 비율이 10% 를 넘으면 결과에 "점수대 기록이 얇음" 표시.
4. **내 흐름 맞추기**(첫 안의 "내 실력 차" 항은 뺐다 — 경기당 초과분 × 하루 100판 × 40일이 다시 한 방향 폭주를 만들고, 지난 상승을 두 번 센다, 검토 B 2-1):
   걸음을 뽑을 때 **바로 앞 사흘 ELO 변화가 같은 3분위**인 구단주를 고른다. 기준은 **그 경로 자신의 직전 사흘 — 날마다 다시 잰다**(첫날만 내 실제 기록, 그 뒤는 경로가 만든 값).
   내 기록이 없으면 첫날은 맞추지 않는다. 내 최근 사흘로 60일을 고정하면 "사흘 연승한 사람"의 걸음만 계속 뽑혀 위로 쏠린다(검토 B 3-1).
   **칸이 얇을 때 푸는 순서**: ① 3분위 맞추기 ② 띠 ±100 → ±200 ③ 그날 0. 문턱(`PREDICT_MIN_STEPS`·`PREDICT_MIN_BLOCKS`)은 **3분위까지 나눈 칸** 기준으로 잰다(검토 B 3-4).
   3분위 경계는 **같은 띠(±50) 안의 사흘 변화로** 잰다 — 표본 전체로 재면 높은 점수대는 사흘 변화가 작아 거의 다 가운데 칸에 몰려 ①이 늘 풀린다(검토 B 4-3). 띠별 경계 실측값은 장부에.
5. 끝 ELO 를 그 경로의 **최종 컷**과 대어 순위.
- **최종 컷**(검토 B 14 — 첫 안의 `a + b·ln(day)` 는 7일로 기울기가 안 정해져서 뺐다): 경로마다 받은 시즌(`PREDICT_FETCH_SEASONS`) 전부 중 하나를 **시즌 길이가 그 경로 종료일과 가까울수록 크게** 뽑고,
  그 시즌의 최종 컷(10개 순위 · log-순위 보간)을 쓴다. 단 각 순위 컷은 **지금 스냅숏의 컷보다 낮지 않게**(`max`).
  **추정(장부에 "추정")**: 최근 4시즌 200위 최종 컷은 ±21 안이지만 80·70시즌은 약 80점 낮았다(R3) — 넷만 쓰면 시즌 사이 흔들림이 작게 잡힌다(검토 B 2-7).
  그래서 **받는 시즌을 늘린다** — `PREDICT_FETCH_SEASONS = 8`(쪽 80개, 한 번만) · 뽑기는 받은 시즌 전부에서 길이 가중(첫 안의 `PREDICT_PAST_SEASONS` 하나를 둘로 — 검토 B 3-6).
  **잡음은 더하지 않는다** — 실제 시즌 하나를 뽑은 위에 시즌 간 표준편차를 또 더하면 흔들림을 두 번 센다(검토 B 3-5). 한 경로는 **한 시즌의 컷 줄 전체**를 쓰므로 200위 컷 > 1,000위 컷 순서가 깨지지 않는다.
  `max(지금 컷)` 은 뽑은 시즌 값에 순위마다 건다(그래도 순서는 유지 — 지금 컷도 순서대로라).
  **추정(장부)**: 시즌 후반에 지금 컷이 지난 시즌 최종 컷을 넘으면 `max` 가 지금 컷을 그대로 써서 남은 상승이 빠진다 → 200위 확률이 부풀려질 수 있다(검토 B 4-4).
  지난 시즌의 "같은 경과일 컷 → 최종 컷" 상승 폭은 시즌 중간 스냅숏이 있어야 잴 수 있어(지금 없음) 1.3.1 에선 못 넣는다 → 지금 컷이 뽑은 최종 컷을 넘는 경로가 10% 를 넘으면
  결과에 "시즌 후반 — 컷 상승을 다 반영하지 못합니다" 를 붙인다. 한 시즌 스냅숏이 모이면 그 상승 폭을 더하는 방식으로 바꾼다(1.3.x). 테스트 `test_late_season_cut_warning`.
  시즌이 2~3개뿐이면 길이 가중 없이 같은 무게(검토 B 2-8). 테스트 `test_cut_spread_follows_seasons`(같은 값 시즌 여덟 vs 흩어진 여덟 → 확률 범위가 넓어짐 · 모든 경로에서 200위 컷 ≥ 1,000위 컷).
  1만 위는 목표에서 뺐으므로 길이 의존(R4)이 결과에 거의 안 닿는다.
- `PREDICT_RUNS = 2000` · 걸음은 미리 (점수대, 칸) 로 묶어 둔다 → 경로 × 남은 날(≤ 70) 번 뽑기 ≈ 14만 번, 표준 `random`(R13), **시뮬레이션 ≤ 300ms**.
  `day_steps`(원본 약 14 스냅숏 × 1만 행 읽기·잇기)는 따로 — **마지막 스냅숏 id 로 캐시**(하루 한 번만 다시 만든다), 시간은 구현 때 따로 재서 예산 표에(검토 A 2-6). `PredictWorker`(작업 스레드)에서 — 수집 완료·검색 완료 때 `EloLoader` 뒤에 이어서(검토 A 11).
  결과는 (ouid, 마지막 스냅숏 id, 마지막 경기 id, 종료일 출처) 키로 캐시.
- 상수는 `config.py` 한 곳(`PREDICT_*`).

**숫자를 낼 조건과 못 낼 때 문구**(검토 B 5·7·9 — 원인마다 다른 말):

## 1.4.1 — 넥슨 API 분석

- **거래 기록 수집** — `nexon_api.get_trades(ouid, tradetype, offset, limit)` · `store.trades(ouid, sale_sn PK, type, date,

  **검색한 계정 본인 화면에만** 쓴다(남의 지출을 들여다보는 기능은 만들지 않는다).

  `store.card_prices(spid, grade, price, fetched_at)` 에 하루 캐시. 2.1.1 에서 급여·OVR 로 넓힌다.

- **새 메뉴 "스쿼드·이적"** — 타임라인 / 가계부 두 화면(1.x 라 페이지 안 탭 대신 메뉴 두 줄, 2.1.1 에서 탭으로).

## 버전 미정 후보

### 시즌 구분을 경기의 시즌 번호로 (1.1.1 때 나온 것)
지금 시즌별 성적·시즌 필터는 데이터센터 시즌표를 읽어야 해서 홈페이지 데이터를 끄면 안 된다. 감독모드 경기는 전부 `seasonId` 가
있으니 그 번호로 나누고, 시즌표는 기간(날짜) 표시에만 → 홈페이지 데이터를 꺼도 시즌 구분이 된다. 어느 버전에 넣을지 미정.
