## 버전 규칙

`a.b.c` — **a** 큰 패치(구조가 바뀌어 새로 익혀야 함: 메뉴 재편 · 저장 형식 큰 변경) · **b** 중간(새 기능·화면) ·
**c** 작은 수정(버그·문구·작은 성능). 섞이면 큰 쪽을 올리고 **아래 자리는 1로** 돌린다(1.4.2 → 2.1.1).
예외: 공개판 1.0.2 의 가운데가 0 이라 창 크기 수정만 1.0.3, 다음 기능 패치(1.1.1)부터 새 규칙.
`updatecheck` 는 세 자리 숫자 비교라 이 체계에서 그대로 동작한다.

## 모든 버전 공통 — 끝났다고 보는 기준

1. 새 코드마다 테스트 + **일부러 되돌린 변이가 FAIL** 하는지(`mutate.js` 또는 손 변이). 커밋 메시지에 "변이 N건 FAIL".
2. 테스트 7종 통과 · CI 초록 · `check_api.py` 에 새 출처마다 한 줄.
3. 1만 경기 계정으로 **검색→첫 화면 · 메뉴 전환 시간**을 이전 값과 비교(지금: 마지막 계정 약 1.3초, 메뉴 0.3초 이하).
4. 창 1280×720(1.0.3 뒤로는 작은 화면 최소 높이 포함)에서 잘림 없음 — 기존 offscreen 테스트.
5. exe 빌드 → 2번 모니터 스모크(창을 띄워야 할 때) · 크래시 로그 증가 0.
6. `CHANGELOG.md` 절 · README · 프로젝트 `CLAUDE.md` 파일 표 갱신 → `release.py` → 공개 명령은 사용자.
7. 홈페이지(데이터센터)를 새로 읽는 기능은 전부 `config.WEB_DATA` 뒤 + `test_web_data_switch_blocks_every_request` 에 등록.
   이용 안내 문구가 실질적으로 바뀌면 `NOTICE_VERSION` 을 올린다.
8. 화면이 쓰는 새 분석 함수는 `core_api.py` 의 import 와 `__all__` 에 한 줄(19단계 경계 — 안 하면 경계 테스트가 FAIL).
   지우는 함수는 거기서도 뺀다.

"한 회차에 새로 나온 게 0개면 끝"은 세 번 틀렸다(1단계 3회차 · 2단계 3회차 · 2단계 재측정 전). 늦게 나온 결함 14개를

**모든 패치(a·b·c)에 ①~⑩·⑫**(2026-10-04 사용자: "무겁더라도 모든 패치에"). **내 검토는 준비 단계** — 계획을 쓴 사람이라
같은 곳을 못 본다. 실측: 내가 6회 반복해 "0개"라 한 1.1.1 계획에서 독립 검토자 둘이 각 25개 안팎의 진짜 결함을 찾았다

**끝내는 조건 — 모두 만족해야**: 주장 장부에 "추정"이 없다(구현 때만 잴 수 있는 건 **잴 테스트 이름까지** 적고 넘긴다) ·
환경 행렬에 빈칸이 없다(실제 윈도우 칸은 구현 뒤 필수) · 마지막 회차는 고친 부분이 아니라 **계획 전체**에 ①~⑩·⑫ ·
**독립 검토자가 새 [상] 결함 0개**(새 [중]·[하]는 계획에 적고 구현 때 테스트로 잡는다) · 보고에 **"재지 않은 것"** 목록을 붙인다.

**검토를 돌리는 방법 — 토큰 아끼기**(2026-10-04 사용자: "토큰 사용이 너무 심하다" → 아래 여섯 가지로). 실측: 검토자 1명이 회당
13만~19만 토큰, 1.1.1 은 2명 × 4회차로 100만 넘게 들었다 — 대부분 큰 파일(`app_main.py` 약 4,800줄)을 매번 처음부터 읽는 데 썼다.
1. **계획이 끝나면 새 세션에서 구현** — 긴 세션은 답할 때마다 쌓인 맥락 전체를 다시 읽는다. 정본은 이 문서라 새 세션은 여기만 읽고 시작한다.
2. **다음 회차는 같은 검토자를 이어 쓴다**(SendMessage) — 이미 읽은 코드를 다시 안 읽는다. "이 줄들이 바뀌었으니 거기만"으로 시킨다.
3. **보고는 짧게** — [상]·[중]만, 결함마다 한 줄 근거, "확인한 것" 목록 없이.
4. **이미 잰 사실은 장부로 넘긴다** — 계획 머리말의 실측값은 다시 재지 말라고 적어 준다(넥슨 요청 속도·DB 내용을 매 회 다시 쟀다).
5. **계획은 고칠 곳만 고친다** — 절 전체를 새로 쓰지 않는다(4차에 20군데 교체로 바꿨다).
6. **[중]·[하]는 구현하면서 테스트로** — 최근 회차 결함 대부분이 "구현 뒤 실측"·테스트로 바로 잡힐 성격이었다. 그래서 끝내는 조건이 [상] 0개다.

## 배포 보호 준비 (2026-10-05 사용자와 결정 — 19단계 끝 · 20~22단계는 나중)

**목표**: 기능이 거의 완성되면 핵심 알고리즘을 쉽게 베끼지 못하게 배포한다. **지금은 개발 편의 우선** — Nuitka·난독화·보호 빌드는 적용하지 않는다.

**정한 것**
- **저장소는 공개 유지(MIT).** 비공개 전환은 기각 — 기존 설치자의 자동 업데이트(`config.LATEST_RELEASE_API`)·릴리스 링크·`.iss` URL·UA 의 주소가
  전부 끊기고, 이미 공개된 커밋의 MIT 허락은 회수되지 않는다.
- **핵심만 가린다** — 그때 가치 있는 알고리즘(예측 등)만 비공개 저장소로, 공개 저장소엔 약속(`core_api`)과 간이 대체만. 배포판엔 **Nuitka 로
  컴파일한 `.pyd`**. 이미 공개된 `analysis.py`·`stats.py` 는 못 가린다 — 가려지는 건 분리 뒤 새로 만들거나 크게 바꾼 것부터.
- **PySide6 전환이 선행 조건** — PyQt6 는 GPL v3 라 숨긴 모듈을 묶은 exe 를 배포하면 위반이다(LGPL 인 PySide6 는 Qt DLL 을 바꿔 끼울 수 있게만 두면 된다).

### 2 연승·연패 뒤 승률 (7단계)

- `stats.after_streak_rates(matches, max_len=3) -> list[StreakAfter]` — `StreakAfter(kind "승"|"패", length 1..3(3 = 3+), win, draw, lose)`.
  입력은 최신순 `MatchSummary`(화면 순서) → 안에서 날짜순으로. 규칙은 `longest_streaks` 와 같게: 몰수도 승패(M2 — 결과 문자열이 이미 승/패), 무·오류는 연속을 끊는다,
  **다음 경기가 승·무·패가 아니면(오류) 분모에서 뺀다**. 날짜 없는 경기는 뺀다. 시간 간격 조건은 두지 않는다(M4 — 효과가 없었다).
- 화면: 흐름 분석 아래 구역 "연승·연패 직후 승률" — 여섯 줄 `win_rate_bar` + 전체 승률 기준 대비 `±%p`. 범위는 흐름 분석과 같은 시즌 범위(`self._matches`).
  **이 구역의 흐림 기준은 문장 기준과 같게 `max(MIN_COND, COND_SHARE × 전체)`**(검토 B — 막대는 굵은데 문장은 침묵하는 엇갈림을 없앤다). 구역 안내에 "흐린 줄은 표본 N경기 미만" 을 적는다.
- `narrate` 규칙: `|차이| ≥ GAP`(10%p) **이고** 표본 ≥ `max(MIN_COND, COND_SHARE × 전체)` 일 때만 한 줄. **실측상 거의 안 나온다(M4) — 그게 맞는 결과**(침묵이 틀린 단정보다 낫다).
  대신 구역의 기준 대비 숫자가 "연패 뒤에도 승률이 거의 같다"는 사실을 보여 준다.
- `core_api` import·`__all__` 한 줄.
- 테스트(`test_parsing`): 손으로 만든 순서(승승패승… · 무가 끊음 · 오류 다음 경기 제외 · 3+ 묶음 · 입력 순서 무관). 변이: `min(run, max_len)` → `run` · 무를 안 끊게 · 오류 제외 빼기 → FAIL.
  `test_analysis`: 차이 12%p·표본 충분이면 한 줄, 9%p 면 침묵(경계).

- **실패**: maxdivision 실패·느림 → 처음이면 줄 숨김, 같은 계정이면 보던 값 유지, 검색은 그대로(신호 분리) · 델리게이트 그리기 예외 → 기본 그리기로 넘기고 한 번만 기록(⑦).

  (업데이트 뒤 상태줄 안내 같은 장치는 두지 않는다 — 윈도우 알림 0·초점 뺏기 금지와 별개로, 흐림·⚠ 는 툴팁이 스스로 설명한다):
  ① 몰수 판정 변경 → "경기 결과"의 정상 종료 승·패 수가 줄고 몰수 줄이 생긴다(실데이터 512팀-경기). CHANGELOG 에 "줄어든 만큼이 몰수로 따로 세어진 것" 을 직접 쓰고,
  몰수 줄 툴팁에 판정 기준("넥슨 경기 종료 유형 — 상대·내가 나가서 끝난 경기")과 **"승률 계산에는 아직 안 들어간 경기(내 쪽 기록이 '오류'인 몰수패) 포함"** 을 단다.

  ③ 표본 흐림·⚠ 가 새로 보인다 — CHANGELOG 한 줄.
- **예산**: 넥슨 오픈API 검색당 +1건, 재시도 없음(호출 한도 1,000/일 개발 키에서도 무시할 수준 · 상세 받기가 끝난 뒤라 그 슬롯에 영향 없음) · 화면 그리기 증가 ≤ 50ms(흐름 분석·성적 진단·선수 지표 각각, 1만 경기) · 메모리 증가 없음(새 캐시 없음).
