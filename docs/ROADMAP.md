## 버전 규칙

`a.b.c` — **a** 큰 패치(구조가 바뀌어 새로 익혀야 함: 메뉴 재편 · 저장 형식 큰 변경) · **b** 중간(새 기능·화면) ·
**c** 작은 수정(버그·문구·작은 성능). 섞이면 큰 쪽을 올리고 **아래 자리는 1로** 돌린다(1.4.2 → 2.1.1).
예외: 공개판 1.0.2 의 가운데가 0 이라 창 크기 수정만 1.0.3, 다음 기능 패치(1.1.1)부터 새 규칙.
`updatecheck` 는 세 자리 숫자 비교라 이 체계에서 그대로 동작한다.

## 모든 버전 공통 — 끝났다고 보는 기준

1. 새 코드마다 테스트 + **일부러 되돌린 변이가 FAIL** 하는지(`mutate.js` 또는 손 변이). 커밋 메시지에 "변이 N건 FAIL".
2. 테스트 7종 통과 · CI 초록 · `check_api.py` 에 새 출처마다 한 줄.
3. 1만 경기 계정으로 **검색→첫 화면 · 메뉴 전환 시간**을 이전 값과 비교(지금: 마지막 계정 약 1.3초, 메뉴 0.3초 이하).
4. 창 1280×720(1.0.3 뒤로는 작은 화면 최소 높이 포함)에서 잘림 없음 — 기존 offscreen 테스트.
5. exe 빌드 → 2번 모니터 스모크(창을 띄워야 할 때) · 크래시 로그 증가 0.
6. `CHANGELOG.md` 절 · README · 프로젝트 `CLAUDE.md` 파일 표 갱신 → `release.py` → 공개 명령은 사용자.
7. 홈페이지(데이터센터)를 새로 읽는 기능은 전부 `config.WEB_DATA` 뒤 + `test_web_data_switch_blocks_every_request` 에 등록.
   이용 안내 문구가 실질적으로 바뀌면 `NOTICE_VERSION` 을 올린다.
8. 화면이 쓰는 새 분석 함수는 `core_api.py` 의 import 와 `__all__` 에 한 줄(19단계 경계 — 안 하면 경계 테스트가 FAIL).
   지우는 함수는 거기서도 뺀다.

## 배포 보호 준비 (2026-10-05 사용자와 결정 — 19단계 끝 · 20~22단계는 나중)

**목표**: 기능이 거의 완성되면 핵심 알고리즘을 쉽게 베끼지 못하게 배포한다. **지금은 개발 편의 우선** — Nuitka·난독화·보호 빌드는 적용하지 않는다.

**정한 것**
- **저장소는 공개 유지(MIT).** 비공개 전환은 기각 — 기존 설치자의 자동 업데이트(`config.LATEST_RELEASE_API`)·릴리스 링크·`.iss` URL·UA 의 주소가
  전부 끊기고, 이미 공개된 커밋의 MIT 허락은 회수되지 않는다.
- **핵심만 가린다** — 그때 가치 있는 알고리즘(예측 등)만 비공개 저장소로, 공개 저장소엔 약속(`core_api`)과 간이 대체만. 배포판엔 **Nuitka 로
  컴파일한 `.pyd`**. 이미 공개된 `analysis.py`·`stats.py` 는 못 가린다 — 가려지는 건 분리 뒤 새로 만들거나 크게 바꾼 것부터.
- **PySide6 전환이 선행 조건** — PyQt6 는 GPL v3 라 숨긴 모듈을 묶은 exe 를 배포하면 위반이다(LGPL 인 PySide6 는 Qt DLL 을 바꿔 끼울 수 있게만 두면 된다).
- **암호화(PyArmor 류)는 안 쓴다** — 실행 때 어차피 풀리고, 모르는 사람에게 주는 exe 라 백신 오탐이 치명적. 컴파일만으로 원문 복원 도구가 안 통한다.
  결과를 보고 공식을 추정하는 것·기계어 분석은 어떤 방법으로도 못 막는다(완전히 막으려면 서버 — 지금 규모엔 과함).
  **기대치**: "파일을 AI 에 던져 원문 받기"는 막지만, Nuitka 는 속성 이름·문자열·상수가 바이너리에 남고 흐름이 C API 호출 나열이라
  디스어셈블러 + AI 로 시간을 들이면 이 규모의 통계 공식은 대부분 되살아난다고 본다. 정말 지킬 알고리즘이 생기면 그것만 서버로 — 그때 다시 판단.
- **카카오톡 봇은 완전히 안 한다**(사용자) → 19단계에서 지웠다(`cf8491d`).

**19단계 ✅ 끝(2026-10-05, 1.2.1 에 실림 · 기능 변경 없음)** — 봇 삭제 · 화면 ↔ 분석 경계 `core_api.py` · 저장소 주소 한 곳(`config.REPO_SLUG` · `.iss` 의 `RepoUrl`).
**6~18단계의 새 분석 코드는 `core_api` 를 거친다**(화면 파일이 analysis·stats·models 를 직접 import 하면 `test_ui_reaches_analysis_only_through_core_api` 가 FAIL).

## 1.4.1 — 넥슨 API 분석

> **사용자 결정(2026-10-06)**: ① 거래 기록은 **내 계정에만** 붙인다 — 넥슨이 검색 계정이 아니라 **API 키 주인**의 거래만 준다(R1·R2).
> 그래서 1.3.1 때 뺀 "내 계정" 지정이 **거래 화면에 필요한 만큼만** 들어온다(다른 화면은 지금처럼 검색한 계정 기준).
> 로드맵 첫 안("검색한 계정 본인 화면에만 · `get_trades(ouid, …)`")은 실측으로 성립하지 않았다.

**규모** 큼. 새 넥슨 요청: 오픈API 둘(거래 · 랭커 기록) + 홈페이지 하나(시세 — 이미 있는 카드 상세 요청을 캐시로).

### 내 계정 지정 · 거래 수집 (11단계 · ✅ 끝 2026-10-06)

> 구현 메모: 받는 규칙은 Qt 없는 `tradecollect.collect`(가짜 API 로 끊김·겹침·429·키 바뀜 테스트), `app_main.TradeLoader` 는 감싸기만.
> 띠 자리는 12단계 메뉴를 미리 — `NAV` 에 "스쿼드·이적 › 이적시장 가계부" 한 줄(띠 + 받기 상태 줄 + "가계부 표는 준비 중"), 12단계가 타임라인 줄과 표를 더한다.
> 첫 수집이 끊긴 뒤의 `top_stop` 은 ""(첫 수집 표시)를 저장된 최신으로 다시 잡는다 — 첫 수집 덩어리는 맨 위부터 이어져 있어 안전하고, 안 그러면 다시 빈 쪽까지 160요청을 되읽는다.
> 끊긴 일반 위쪽(경계가 진짜 날짜)은 그대로 둔다(2회차 [상]). `done` 은 위쪽이 빈 쪽에 닿아도 참.
> `TradeLoader.done` 은 스레드 안에서 나와 그 순간 `isRunning` 이 참 — 화면 다시 그리기는 `finished` 에서(안 그러면 "받는 중…"이 남는다).
> `stats.trade_hint` 의 DISTINCT 는 SQL 대신 집합(규칙 검사 `TEMP B-TREE`). `test_trades` 를 `test_rules` 의 SQL 추적에 넣었다.

- **API**: `nexon_api.EP_USER_TRADE` · `get_trades(tradetype, offset, limit=100)` — **ouid 인자가 없다**(넥슨이 무시 — R1. 받는 척하면 남의 거래로 읽힌다).
  ouid 를 아예 빼고 부를 수 있는지는 구현 첫 줄에서 잰다(안 되면 빈 문자열 — R1 에서 통과). `TRADE_PAGE = 100`(R4 상한).
- **저장**(fifa.db): `trades(kind TEXT, sale_sn TEXT, trade_date TEXT, spid INTEGER, grade INTEGER, value INTEGER, PRIMARY KEY(kind, sale_sn))` +
  `idx_trades_spid(spid, trade_date)` · `INSERT OR IGNORE`(R5 중복 — 같은 줄이 별개 판매였는지는 사용자 대조, 아래 "재지 않은 것"). ouid 열은 **없다** — 이 표는 "이 키 주인의 거래"다.
  `trade_state(key TEXT PRIMARY KEY, value TEXT)`: `key_fp`(키 sha256 앞 16자 — 키 자체는 안 남긴다) · `fetched_at` · `my_ouid` · `my_ouid_unconfirmed`(키가 바뀐 뒤 확인 전) · 종류별 `done_<kind>`(가장 옛 쪽까지 닿았다) ·
  종류별 `top_stop_<kind>`(위쪽 받기를 **시작할 때** 저장돼 있던 최신 거래 날짜 — 위쪽이 끝나면 지운다).
- **키가 바뀌면 — 판정하지 않고 전부 다시 받는다**(4회차에 설계를 줄였다). 1~4회차에 "같은 주인인가"를 `saleSn` 대조로 판정하려다 회차마다 새 [상]이 나왔다
  (판정 전 쓰기로 자기 오염 · 0건·빈 쪽·20쪽 미정 · 구매 `saleSn` 은 판 사람의 매물 번호라 부계정 매물을 사면 종류를 넘어 겹침 · 묻는 띠의 상태·반복 요청).
  틀렸을 때 잃는 것은 다시 받기(162요청 · 약 19초 — R4)뿐이라 판정 장치의 위험이 이득보다 크다.
  - 감지: `TradeLoader` 가 **시작할 때마다** `trade_state.key_fp` 와 지금 키(`config.API_KEY` — 모듈 경유)의 지문을 비교한다 — 키를 바꾸는 길 셋(`_ask_new_key` app_main.py:3342 ·
    첫 실행 키 창 · `.env` 손 수정)을 한 자리에서 잡는다.
  - 다르면 **한 트랜잭션으로** 거래 · `done_*` · `top_stop_*` · `fetched_at` 을 **전부** 지우고 `key_fp` 를 새것으로, `my_ouid` 는 `my_ouid_unconfirmed` 로 옮긴다(`my_ouid` 가 비었으면 — 확인 전에 키가 또 바뀜 — **기존 unconfirmed 를 그대로 둔다**) → 그다음 첫 수집처럼 받는다.
    커밋 뒤 로더가 **"지웠음" 신호**를 내고, 화면은 거래를 쓰는 메뉴 전부를 `_invalidate` 해 다시 읽는다(지연 그리기가 들고 있던 옛 주인 거래가 남지 않게 · `test_trade_wipe_clears_screen`).
  - **띄우는 때**: 검색 끝 외에 **키를 바꾼 직후**(`_ask_new_key`·첫 실행 키 창 뒤)와 **거래 화면을 열 때** — 그리고 지문이 다르면 `fetched_at`·`done_*` 하루 제한과 **무관하게** 띄운다
    ("API 키 확인 중"이 검색할 때까지·다음 날까지 안 풀리지 않게 · `test_key_change_starts_loader_same_day`).
  - 화면: 거래 화면은 `my_ouid_unconfirmed` 가 있으면 거래를 붙이지 않고 띠 *"API 키가 바뀌었습니다. 내 계정이 ○○ 맞나요? [맞음] [바꾸기]"* + 1회차 힌트(%) —
    다시 받기가 끝나기 전엔 힌트 자리에 *"거래 기록을 다시 받는 중 — 끝나면 힌트가 나옵니다"*, 끝나면 갱신. 답은 화면 스레드가 `my_ouid` 한 줄만 쓴다
    (받기와 무관 — 답을 안 해도 수집은 계속되고 요청이 되풀이되지 않는다). [맞음]을 잘못 눌러도 [바꾸기]로 되돌린다(1회차 띠와 같음).
  - 화면이 지금 키의 지문 ≠ `key_fp` 를 보면(로더가 아직 안 돔) 거래 화면은 *"API 키 확인 중"* — 새 키 주인이 옛 주인 가계부를 자기 것으로 읽지 않게.
  - 키 교체 직후 돌던 `TradeLoader` 엔 `cancel()` 만(**화면 스레드에서 `wait()` 안 함**), 끝남 신호 뒤 새로 띄운다(`TradeLoader` 는 한 번에 하나).
- **받는 규칙**(1회차 [상] — 첫 수집이 끊기면 옛 거래가 영영 빠졌다):
  - **위쪽(새 거래)**: 시작할 때 `top_stop_<kind>` 가 없으면 지금 저장된 최신 날짜로 적는다(있으면 끊긴 위쪽을 잇는 중 — 그대로 둔다). offset 0 부터
    **그 쪽의 가장 옛 날짜가 `top_stop_<kind>` − `config.TRADE_OVERLAP_DAYS`(7) 이하**일 때까지(R6 — 늦게 반영된 옛 날짜 거래도 겹쳐 받는다). 다 받으면 `top_stop_<kind>` 를 지운다.
    저장된 거래가 0건이면(첫 수집) `top_stop` 은 "없음" — 위쪽은 빈 쪽까지 가고, 그 빈 쪽으로 `done_<kind>` 도 참이 된다.
    "저장된 `saleSn` 을 만나면 멈춤"은 **쓰지 않는다** — 끊긴 직전 실행이 넣은 새 묶음으로도 채워져 가운데 구멍이 영구히 남았다(2회차 [상]). 끊긴 뒤엔 0쪽부터 다시 읽는다(`OR IGNORE`).
  - **아래쪽(옛 거래)**: `done_<kind>` 가 아니면 offset = max(0, 그 종류 저장 줄 수 − 100)부터 빈 쪽이 올 때까지 → 빈 쪽에서 `done_<kind>`. 새 거래가 위에 끼면 offset 이 밀려 **겹칠 뿐 건너뛰지 않는다**.
  - **쪽마다 한 트랜잭션** — 끊겨도 반쪽 쪽은 롤백. `cancel()` 은 쪽 사이에서 본다. `fetched_at` 은 위쪽이 두 종류 다 끝났을 때만 쓴다.

  - 첫 수집 요청 162 · 약 19초(R4). 위쪽은 **하루 한 번**(`fetched_at` 이 오늘이면 안 부른다), 아래쪽은 끝날 때까지 기회마다.

### 스쿼드 타임라인 (12단계) — `squad_timeline.py`

- 입력: 검색 계정의 경기 + (내 계정일 때만) 거래. 출력: `TimelineEvent(date, spid, kind, grade_from, grade_to, before, after)` 목록.
- 사건 종류: 구매 · 판매 · 첫 출전 · 마지막 출전 · 강화 변화(같은 `spid` 의 `spGrade` 가 바뀐 첫 경기). 같은 카드를 여러 번 사고팔면 구간을 나눈다.
- 짝 안 맞은 구매(판 기록 없음)의 상태 — **위에서부터 먼저 맞는 것**(2회차: 조건이 겹쳤다):
  1. **보유 중** — 최근 `config.HOLD_RECENT_GAMES`(50)경기 스쿼드에 나왔다. **같은 `spid` 의 짝 안 맞은 구매가 여러 장이면 가장 최근 구매 한 장에만**
     (스쿼드엔 한 장 — 나머지는 강화 재료일 수 있어 평가가 두 배가 된다, 3회차) — 나머지는 아래 순서로
  2. **최근 구매 · 아직 안 씀** — 산 지 `config.HOLD_GRACE_DAYS`(14)일 안. **평가 손익 합계에 넣지 않고 따로 소계**(강화 재료로 산 카드가 14일 동안 합계를 흔들지 않게 — 3회차)
  3. **미출전 · 보유 여부 모름** — 산 뒤 한 번도 안 썼다
  4. **최근 50경기에 안 씀 · 보유 여부 모름** — 나머지(강화 재료·방출·보관 — 판매 목록에 안 나오는 길, 1회차 [상]). "행방 모름" 같은 단정 대신 **근거를 문구에**.
  경기가 50보다 적은 계정은 있는 경기 전부로 본다 — 그래서 4번이 늘 수 있고, 띠에 *"최근 N경기 기준"*. · **추정**(거래 없이 스쿼드에 들어옴 — 팩·보상, 2022-01-27 전 구매(R4), 또는 다른 계정이면 전부).
- 사건마다 앞뒤 `config.TIMELINE_WINDOW`(20)경기 승률·득실 — 표본 흐림 규칙(1.2.1) 그대로. 문구는 "들어온 뒤 20경기"(원인 단정 금지).
- 예산: 1만 경기 + 거래 1.6만 줄 한 번 훑기 **300ms 이하**(`test_timeline_budget_10k`).

### N3 이적시장 가계부 (12단계 — 내 계정만)

- **짝은 전체 이력으로 먼저 맞추고, 범위는 그 뒤에 자른다** — 시즌 콤보로 거래를 먼저 자르면 지난 시즌에 사서 이번 시즌에 판 카드가 "취득가 없음"이 된다.
  실현 손익은 **판매 날짜**로, 지출은 구매 날짜로 범위에 넣는다. 총 지출 · 수입 · 순지출.
- 짝: **같은 `spid` 끼리 선입선출**(강화는 산 뒤 바뀔 수 있어 `grade` 는 짝 기준이 아니라 표시). 판 것 → **실현 손익**, 짝 없는 판매 → *"취득가 없음"*(팩·보상) 따로 합계.
  팩으로 받은 같은 카드가 섞이면 짝이 틀릴 수 있어 화면에 *"짝은 먼저 산 것부터 맞춘 추정"*.
  짝은 **판매일 ≥ 구매일**인 구매하고만. 옛 거래를 아직 다 못 받았으면(`done_*` 거짓) 실현 손익은 비우고 *"거래 기록을 받는 중"*(뒤 구매와 잘못 짝지어지지 않게).
  **보유 중**(타임라인 1번)만 **평가 손익** = 오늘 시세(지금 강화 = 마지막 출전 `spGrade`) − 산 값. 2번은 *"최근 구매(아직 안 씀)"* 소계(시세는 산 강화 기준)로 따로,
  3·4번은 평가하지 않고 건수·산 값 합계만. 시세가 없으면 빈칸.
- **수수료**(R7): 11단계 첫날 사용자가 게임 안 거래 내역 한 줄과 대조한다(사용자 확인 필요) → 결과에 따라 문구 *"판매 금액은 수수료를 뗀 값"* 또는 계산.
  **대조 전에는 실현 손익(판매 금액)과 평가 손익(홈페이지 시세 — 수수료 전)을 한 합계로 더하지 않는다** — 기준이 다르다. 화면 고정 문구 *"이적시장 기준(강화 비용 제외)"*.
- 큰 금액 표시는 **새로 만들지 않고** `ranker.format_team_value`(ranker.py:365 · `_VALUE_UNITS` 억·조)를 쓴다 — 같은 단위 표가 두 벌이 되지 않게.

지금 시즌별 성적·시즌 필터는 데이터센터 시즌표를 읽어야 해서 홈페이지 데이터를 끄면 안 된다. 감독모드 경기는 전부 `seasonId` 가
있으니 그 번호로 나누고, 시즌표는 기간(날짜) 표시에만 → 홈페이지 데이터를 꺼도 시즌 구분이 된다. 어느 버전에 넣을지 미정.

---

### "내 계정" 지정 (1.3.1 검토 때 뺐다 — 2026-10-05 사용자: "일단 빼놓고 후보로")
트레이 알림(1.1.1 8절 — 뺐다) 때문에 필요했던 설정이다. 알림이 없으니 ELO 그래프·순위 구간 변화는 **지금 검색한 계정** 기준으로 충분하다.
다시 볼 조건: 켤 때 특정 계정을 기본으로 보여 달라는 요청이 생길 때. (수집 때 따라가는 계정은 1.3.1 의 "따라가기 목록(최대 5명)"이 맡는다 — 사용자 ⑥.)

---

### 내 쪽이 "오류"로 남은 몰수패를 승률에 넣기 (1.2.1 검토 때 나온 것)
나 `matchEndType` 4 + 상대 1 인 경기는 실제로는 몰수패인데 결과 문자열이 "오류"라 승률·연속 분모 밖이다. N7 은 몰수로 세지만
`MatchSummary.result` 는 그대로 뒀다 — 바꾸면 모든 승률이 움직여 따로 판단할 일. 어느 버전에 넣을지 미정.
