## 버전 규칙

`a.b.c` — **a** 큰 패치(구조가 바뀌어 새로 익혀야 함: 메뉴 재편 · 저장 형식 큰 변경) · **b** 중간(새 기능·화면) ·
**c** 작은 수정(버그·문구·작은 성능). 섞이면 큰 쪽을 올리고 **아래 자리는 1로** 돌린다(1.4.2 → 2.1.1).
예외: 공개판 1.0.2 의 가운데가 0 이라 창 크기 수정만 1.0.3, 다음 기능 패치(1.1.1)부터 새 규칙.
`updatecheck` 는 세 자리 숫자 비교라 이 체계에서 그대로 동작한다.

## 배포 보호 준비 (2026-10-05 사용자와 결정 — 19단계 끝 · 37~39단계는 나중)

**목표**: 기능이 거의 완성되면 핵심 알고리즘을 쉽게 베끼지 못하게 배포한다. **지금은 개발 편의 우선** — Nuitka·난독화·보호 빌드는 적용하지 않는다.

**정한 것**
- **저장소는 공개 유지(MIT).** 비공개 전환은 기각 — 기존 설치자의 자동 업데이트(`config.LATEST_RELEASE_API`)·릴리스 링크·`.iss` URL·UA 의 주소가
  전부 끊기고, 이미 공개된 커밋의 MIT 허락은 회수되지 않는다.
- **핵심만 가린다** — 그때 가치 있는 알고리즘(예측 등)만 비공개 저장소로, 공개 저장소엔 약속(`core_api`)과 간이 대체만. 배포판엔 **Nuitka 로
  컴파일한 `.pyd`**. 이미 공개된 `analysis.py`·`stats.py` 는 못 가린다 — 가려지는 건 분리 뒤 새로 만들거나 크게 바꾼 것부터.
- **PySide6 전환이 선행 조건** — PyQt6 는 GPL v3 라 숨긴 모듈을 묶은 exe 를 배포하면 위반이다(LGPL 인 PySide6 는 Qt DLL 을 바꿔 끼울 수 있게만 두면 된다).
- **암호화(PyArmor 류)는 안 쓴다** — 실행 때 어차피 풀리고, 모르는 사람에게 주는 exe 라 백신 오탐이 치명적. 컴파일만으로 원문 복원 도구가 안 통한다.
  결과를 보고 공식을 추정하는 것·기계어 분석은 어떤 방법으로도 못 막는다(완전히 막으려면 서버 — 지금 규모엔 과함).
  **기대치**: "파일을 AI 에 던져 원문 받기"는 막지만, Nuitka 는 속성 이름·문자열·상수가 바이너리에 남고 흐름이 C API 호출 나열이라
  디스어셈블러 + AI 로 시간을 들이면 이 규모의 통계 공식은 대부분 되살아난다고 본다. 정말 지킬 알고리즘이 생기면 그것만 서버로 — 그때 다시 판단.

- A4·C3: 키퍼 키 × 슛 구역별 막아낸 골 · 급여 × 실효 OVR 격자(포메이션 섞지 않는다) · 유효슛 하한 · 표본 당기기 `n/(n+K)`.
- A5: 슛 30개 미만 칸 버림 · 경기장 길이 70% 밖에서 들어간 골 제외(좌표가 골 지점을 안 가리킨다) · 격자는 날짜(패치)별.
- C1: 같은 평균 OVR 이면 수비·미드·공격 어디에 몰아도 1%p 남짓 — 라인 배분 비교.
- C3: 같은 OVR 안에서 어떤 능력치가 이기나(+2 환산 · 견준 차이 8점 넘는 줄은 추천 제외) · 카드 고유 특성의 동급 대비 승률 · 체형.
- D1: 차이가 가장 큰 지표 최대 4개 · 같은 자리 랭커 중 백분위(30판 미만 판정 안 함).
- A3: 승률 그래프의 최근 N판 이동평균 물결은 결과 순서를 섞어도 같은 높이·주기로 나온다(이동 구간 크기가 만든다) — 섞기 기준 띠를 같이 그린다. 무승부만 연속해서 나오는 편(같은 등급대를 연달아 만나서).
- A4·A5: 키퍼 평가는 슛 전체 격자가 아니라 **유효슛 기준 격자**(슛마다 `xg` 와 따로 `xgOnTarget`)로 — 빗나간 슛을 분모에 넣으면 기대 실점이 3분의 1로 나와 부호가 뒤집힌다.
- A6: 연장·승부차기는 **양쪽 모두 챔피언스 이상일 때만** — 경기의 양쪽 `division` 으로 무승부가 가능한 경기였는지 가른다.
- N15: 랭커 강화 단계 분포(11강 비중 등)도 같이.
- N20: 0시대 무승부 급증은 자정 챔피언스 정산(200위 밖 강등)으로 챔스끼리 매칭이 줄어서 — 안내 문구에 적는다.

**재료가 없어 못 하는 것 (2026-10-07 확인)** — 경기마다 오른·내린 랭킹 점수(넥슨 경기 기록에 점수가 없다 — "연승 중엔 이길 때 더 오른다" 류) ·
1만 명 전원 경기가 있어야 하는 리그 기준선의 정확한 값(우리 DB 는 내 경기·상대·랭커 픽뿐 — N24·N25·N27·C3 류는 근사판이고 계획 검토 때 표본부터 잰다).

**넣지 않는 것**: 수수료 계산기 · 스쿼드 메이커(추천 스쿼드 자동) — "하지 않기로 한 것" · 다른 구단주 보상 랭킹 · 랭킹 밖 수집 ·
모든 구단주 경기를 받아야 하는 표(사용자 한 명의 API 키 한도 밖).

### 포메이션별 포지션 특성 (32단계 · 2.5.1) — 계획 3판 (2026-10-07 · 1회차 검토 반영 · 2회차 전)

> **상태: 초안.** 처음 재료는 "주 전술"(팀 전술 10칸 + 개인 전술·참여도)이었다. 25명 실측에서 전술 칸이 한 칸으로 정해지는 사람이 52%뿐이라(R1)
> 사용자가 **팀 전술 설정은 빼고 포메이션 × 포지션 × 부여 특성·코치만** 모으기로 바꿨다(U3 — 2026-10-07).
> 빠진 팀 전술은 "버전 미정 후보"로 옮겼다. 새 웹 출처 · 하루 계수 · 새 표 · 동의 문구 → **검토자 2명**(검토 기준 7번).

랭커가 포메이션마다 각 포지션 선수에게 **실제로 넣어 둔** 일반(5강~)·신규(8강~)·훈련(11강~) 특성과 훈련 코치(최대 3)를 센다.

**규모** 중간~높음. 넥슨 웹 새 호출 1종(POST · 한 명 최대 6요청) · 대상 **1~1,000위**(U4) · 오픈API 는 랭커 픽 길을 그대로 쓰고 범위만 넓히되 **하루 합계는 랭커 픽 300 그대로**(키의 30% — U4) · fifa.db 새 표 1개 · `NOTICE_VERSION` 6 → 7.

#### 사용자 결정 (2026-10-07)

- **U3 포메이션별 포지션 특성만** — 팀 전술·개인 전술·참여도는 안 모은다(판정 52% 문제가 사라진다). 특성·코치가 있는 사람 92%.
- **U2 화면 열 때만** — 201~1,000(오픈API)도 랭커 픽처럼 [특성] 화면과 창이 보일 때만(2.1.1 U2 규칙). 웹도 같은 로더.
- (U1 나눠 쓰기는 전술 판정이 빠져 필요 없어졌다.)
- **U4 대상 1~1,000위**(1회차 검토 뒤) — 초안의 1~2,000 은 오픈API 하루 700(키의 70% — 랭커 픽 300 을 정한 "키의 30%" 원칙 위반 · 검색이 429 로 막힘)과
  배포 사용자 수 × 웹 3,000요청/일, 3일 다시 확인에 하루 600~1,200 이 필요한데 상한 400 이라 갱신이 못 따라가는 문제를 함께 냈다(검토 A·B [상]).
  1,000위 = 추천 범위(`RANKER_RECOMMEND_TOP`)와 같다. 오픈API 는 **랭커 픽과 합쳐 하루 300**(새 계수 종류를 만들지 않는다).
- **U5 분모는 전체 선수**(계획 그대로) — 검토 B 는 "열린 칸 기준"을 권했다(훈련 특성 %가 11강 비율에 좌우된다). 사용자는 "이 포지션 선수 중 몇 %가 넣었나"를 골랐다.
- **U6 다시 묻는 창은 랭킹 수집을 켠 사람에게만** — 꺼진 사람에겐 바뀐 게 없다.

#### 방법 (`traitcollect.py` — 화면 없음)

한 명: 마지막 감독모드 경기(선발 11 · 자리 · 강화) → 팀마다 전술 1 칸(최대 6요청 — 경기 카드가 다 있는 팀을 찾으면 **거기서 멈춘다**) → 경기의 카드마다 그 칸의 `traits`·`trainer` → 저장.
- 포메이션·포지션은 **경기 쪽**(`formation_of` · spposition) — 칸의 글자·role 은 안 쓴다(R2).
- 카드가 다 있는 팀이 없으면 `stale`(낡은 웹 값 — R4) · 저장만 하고 집계에서 뺀다.
- 경기의 강화(`spGrade`)와 칸의 `buildUp` 이 다르면 그 카드만 뺀다(그 사이 강화를 바꿨다 — 열린 칸이 다르다). 구현 때 비율을 잰다(`test_trait_grade_mismatch_dropped`).

#### 다시 확인

마지막 경기 id 가 바뀌었을 때만 · 지난번 팀 칸 하나 먼저(1요청) → 카드가 다 있으면 끝, 아니면 6칸. `stale` 은 `TRAIT_STALE_RETRY_DAYS`(제안 7일) 뒤에만.
마지막 경기는 랭커 픽 길(`rankerpick.due` — 처음 보는 사람·닉네임 바뀐 사람 먼저, 그다음 오래 전에 받은 순 · 닉네임이 같으면 `stale_days` 안엔 안 묻는다).
⚠ 초안의 "스냅숏 승·무·패가 그대로면 안 묻는다"는 **코드에 없다**(`rankerpick.py:134` — 검토 A). 다시 확인은 한 명 최소 1요청(목록) · 새 경기면 2요청.
- 다시 묻는 주기: 1~200 은 랭커 픽 그대로 3일 · 201~1,000 은 `TRAIT_STALE_DAYS`(제안 **10일** — 아래 예산표에서 나온 값).
- **정리(14일)에 닿기 전에 다시 묻는다**: `due` 정렬에서 `fetched_at` 이 `RANK_RAW_KEEP_DAYS − 2`일 넘은 줄을 처음 보는 사람보다 **앞에** 둔다
  (처음 보는 사람을 먼저 받으면 첫 바퀴 동안 첫날 받은 줄이 정리에 걸려 지워지고 다시 "처음 보는 사람"이 된다 — 검토 A·B). `test_trait_recheck_before_prune`.

### 랭커 팀 전술·개인 전술 (2026-10-07 32단계에서 뺐다 — 사용자 U3)
넥슨 웹 스쿼드메이커(`getingameinfo`)에 팀 전술 10칸·선수별 개인 전술·참여도가 있지만 "지금 켜진 칸" 표시가 없다. 마지막 경기 선발과 같은 칸이
딱 하나인 사람이 25명 중 13(52%) — 40% 는 같은 11명·자리로 내용이 다른 칸이 여럿이라 어느 전술을 썼는지 모른다(9위는 10칸 전부). 개인 전술은
그 칸들끼리 44% 만 같다. 32단계 실측 장부 R1~R3 · 코드표 위치 R8. **다시 볼 조건**: 넥슨이 켜진 칸을 알려 주는 값을 내놓거나, 한 칸만 판정된

### 중앙 조회 서버 (2026-10-07 사용자: "서버를 무료로 운영 가능한 곳을 찾기 전까진 놔둔다")
지금은 사용자마다 자기 넥슨 키를 넣는다. 서비스 단계 등록엔 서비스 URL·이미지가 필요한데, 남들이 이 저장소 주소로 각자 등록해도 되는지는
**확인하지 않았다** — 막히면 다들 개발 단계(하루 1,000)로 떨어진다. 웹 서비스처럼 서버가 서비스 키 하나로 대신 조회·캐시하면 이 문제가 사라지지만,
