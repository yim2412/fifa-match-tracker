| 항목 | 값 | 세는 명령 |
|---|---|---|
| 커밋 | **77** | `git log --oneline \| wc -l` |
| 문서 | **512줄** (CLAUDE 127 · README 275 · adapters/README 110) | `wc -l CLAUDE.md README.md adapters/README.md` |
| **커밋 본문** | **658줄** | `git log --format='%b' \| grep -c .` |
| 후보 | **40건** | `awk '/^## 1\. 후보 목록/,/^## 2\./' docs/notes/CANDIDATES.md \| grep -cE "^\\\| \*?\*?[A-G][0-9]+"` |

> **세는 명령을 한 번 고쳤다.** 처음 적은 `grep -cE "^\| [A-G][0-9]+ \|"` 는 **44** 를
> 냈다 — §4 탈락 표의 행(`| A1 | 강하다…`)까지 세기 때문이다. §1 로 범위를 좁혀야
> 40 이 나온다. Argus 에서 개수를 세지 않고 적어 틀린 적이 있어 이번엔 명령을 적었는데,
> **명령을 적는 것만으로는 부족하고 그 명령이 무엇을 세는지도 확인해야 했다.**

**계획서가 이 프로젝트를 "얇다(3순위)"로 잡은 근거는 문서 610줄이었는데**(실측 512),
실제 주 재료는 문서가 아니라 **커밋 본문 658줄**이었다. 전역 규칙이 *"커밋 메시지는
왜를 남긴다"* 를 요구한 덕에, 이 저장소는 문서보다 `git log` 가 두껍다.

> **그래서 "얇다"는 판정이 절반 틀렸다.** 얇은 것은 정리된 문서이고, 판단 기록은
> 얇지 않다. 국방·Argus 에서 배운 *"문서 먼저, `git log` 는 근거 조회용"* 순서가
> **이 프로젝트에서는 뒤집힌다** — 여기서는 `git log` 가 본체다.

## 3. 고른 것 — 2편

**얇은 프로젝트라 억지로 세 편을 채우지 않는다.** 후보는 40건이지만 *한 편을
지탱할 만큼 서사가 이어지는 것* 은 둘이다. 나머지는 좋은 한 문단이지 한 편이 아니다.

### 노트 후보 1 — 정정한 사실을 문서에 다시 심었다 (E1, 보조 E3·E2)

> 판단이 틀렸다는 것을 **커밋 메시지에 정확히 적어 놓고**, 6일 뒤 문서를 정비하면서
> **그 틀린 문장을 다시 타이핑해 넣었다.** 17일 뒤에는 규칙 파일에도 넣었다.
> 오늘 실측으로 여전히 틀리다.

**왜 이것인가.** 허브 주제 「안 여는 문서가 썩는다」가 이미 두 프로젝트에서 나왔는데,
**이건 그 주제의 더 나쁜 변종**이다 — 방치가 아니라 **재기입**이다. 그리고 원인이
구조적이다: **정정은 `git log` 에 남고 문서는 사람이 옮겨 적는다.** 그 사이에
"이 문장이 아직 참인가"를 묻는 단계가 없다.

E3(「나중에」 표가 낡아 4개 중 3개가 이미 도입됨)이 같은 저장소의 두 번째 사례이고,
E2(확인 안 한 것을 단언하지 않는다)가 **반대 방향의 좋은 사례**라 대비가 된다.

| E4·E5·E6 (걷어낸 것들) | *"왜 안 만들었나"* 는 좋은 기록이지만 **실패담이 아니다.** 노트의 성격("무엇이 어떻게 깨졌나")과 다르다 |
| G1·G2 | 최적화 기록이라 성격이 다르다. **G2(병목이 API 가 아니라 DB 되읽기)** 만 "기본 가정이 틀렸다"는 축에서 값이 있다 |
| G3 (혼자 → 여러 명) | **강하다.** 단일 사용자 가정이 무너지는 지점 셋이 한 커밋에 다 있다. 다만 **봇 기능 자체가 이 저장소의 곁가지**(`bot/`·`adapters/`)라, 노트로 쓰면 프로젝트 소개부터 해야 한다. **다음 순번 3순위** |
| G4·G5·G6 | 캐시·정책 판단. 한 문단씩 |

## 5. 허브에 보낼 것 — 새 주제 조건이 찼다

허브 규약은 *"새 주제는 **두 프로젝트 이상**에서 나왔을 때만"* 이다.
**Argus + 피파로 두 개가 된 모양이 셋 있다.**

| 후보 주제 | Argus | 피파 |
|---|---|---|
| **화면이 본문과 다른 말을 한다** | 리포트가 *"원인 프로세스는 특정할 수 없습니다"* 라 적어 놓고 바로 아래 표 제목이 **`원인 후보`** 였다 | 비율은 `—` 로 숨기고 **막대는 실제 길이로** 그렸다 · 문구는 "누적 전체"인데 시즌 필터가 걸려 있었다 |
| **조용히 실패한다** | 자식 stderr 가 `None` 이 되어 실패 원인이 사라짐 · 스레드가 몇 주 죽어 있음 · UI 가 예외를 삼켜 화면만 빔 | **exe 가 아무 말 없이 빈 DB 를 만들어 105경기를 못 봄** · 점검 페이지를 빈 값으로 TTL 내내 캐시 · `pythonw` 에서 `print` 가 죽으면 파일 로그까지 못 남김 |
| **우연히 같은 값이 검증을 통과시킨다** | 코드 기본값과 YAML 기본값이 같아 **배선이 끊겨도 `assert` 가 참** | **"합계"와 "평균×100"이 100경기 표본에서 같아** 참고 사이트와 맞아떨어지는 것처럼 보였다 |

기존 주제에 붙는 것도 있다.

| 기존 주제 | 피파 사례 |
|---|---|
| 통과는 증거가 아니다 | **B1** — `node` 로 ES5 문법을 검사하면 최신 문법을 전부 통과시킨다. 폰에 올린 뒤에야 안다 |
| 안 여는 문서가 썩는다 | **E1** — 정정 6일 뒤 문서에 **다시 심었다.** 썩은 것보다 나쁘다 |

**셋 다 만들지는 않는다.** 세 번째(우연히 같은 값)는 사례 둘이 성격이 꽤 달라
(한쪽은 설정 배선, 한쪽은 통계 표본) 묶으면 억지가 될 수 있다 — **노트를 쓰고
허브를 고칠 때 다시 판단한다.**
