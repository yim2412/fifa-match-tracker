# 정정한 사실을 문서에 다시 심었다

> 판단이 틀렸다는 것을 **커밋 메시지에 정확히 적어 놓고**, 6일 뒤 문서를 정비하면서
> **그 틀린 문장을 다시 타이핑해 넣었다.** 17일 뒤에는 규칙 파일에도 넣었다.
> 49일 뒤인 오늘 실측으로 확인하니 여전히 틀려 있었다.
>
> 2026-07-17 ~ 2026-09-05 · 근거 커밋은 맨 아래

## 시작은 평범한 오해였다

이 앱은 넥슨 오픈API 로 EA SPORTS FC 온라인 전적을 받아 온다. 만들기 시작한 날,
API 가 주는 경기 수를 보고 이렇게 적었다.

> **API는 최근 100경기까지만 준다.** 이 계정은 21시간에 100경기가 쌓여서
> (시간당 약 5경기), 하루만 조회를 걸러도 그 사이 경기는 **영영 못 가져온다** —
> 과거를 조회할 수단이 API에 없다.

`2026-07-17` · `462b1e7`

그럴듯했고, 실제로 이 문장이 **SQLite 누적 저장을 도입한 근거**가 됐다. 조회할 때마다
로컬 DB 에 쌓고 화면은 API 가 아니라 DB 를 그리게 만들었다. 하루라도 안 켜면 그 사이가
영영 뚫린다고 믿었으니 합리적인 결정이었다.

## 다음 날 그게 틀렸다는 걸 알았다

`offset` 페이징을 붙이면서 확인했다. 커밋 메시지에 이렇게 적혀 있다.

> "100경기 더 불러오기": offset 페이징. **확인해 보니 API 는 최근 100경기만 주는 게
> 아니라 offset 으로 3037경기(6/16)까지 과거를 준다. 100은 한 번에 받는 개수 상한일
> 뿐이었다 — 앞서 "과거는 못 가져온다"던 판단이 틀렸다**

`2026-07-18` · `d872ef5`

**정정으로서 흠잡을 데가 없다.** 무엇이 틀렸는지, 실제로는 어떤지, 숫자까지 적혀 있다.
그리고 코드도 그날 바뀌었다 — `get_match_ids` 에 `offset` 인자가 생겼고 화면에
"100경기 더 불러오기" 버튼이 붙었다.

**문서만 안 바뀌었다.**

## 6일 뒤, 그 문장을 다시 적었다

07-24 에 저장소를 정비했다. MIT 라이선스를 붙이고 README 에 개요와 기능표를 썼다.
"누적 저장" 절을 쓰면서 **왜 DB 에 쌓는지**를 설명해야 했고, 그 이유를 옛 서술에서
그대로 옮겨 적었다.

```
2026-07-17  462b1e7   "API는 최근 100경기까지만 준다"          ← 처음 적음
2026-07-18  d872ef5   "그 판단이 틀렸다"                       ← 정정
2026-07-24  07a5f63   "API는 최근 100경기까지만 준다"          ← 다시 적음
2026-08-04  ddcc837   "API가 최근 100경기만 주는데"            ← 규칙 파일에도
```

**썩은 게 아니다.** 방치된 문장이 낡은 것이 아니라, **정정된 지 6일 뒤에 사람이 그
문장을 새로 타이핑해 넣었다.** 그리고 17일 뒤에 규칙 파일(`CLAUDE.md`)에도 넣었다.

## 49일 뒤 — 실측

이 노트를 쓰려고 사실 관계를 확인했다. API 를 한 번 호출했다.

```
get_match_ids(ouid, matchtype=52, offset=N, limit=100)     2026-09-05

  offset=0      100개
  offset=100    100개
  offset=500    100개
  offset=3000    24개     ← 여기서 끝
```

**총 3,024경기.** 100이 아니다. `d872ef5` 가 맞았고 문서가 틀렸다.

그런데 여기서 멈추면 절반만 고치는 것이다. **그럼 누적 저장은 필요 없었나?**

```
API 가 지금 주는 것            3,024경기
같은 시점 fifa.db 의 이 계정   7,859경기   (2026-06-17 ~ 09-04)
```

**필요했다.** DB 가 API 보다 4,835경기를 더 갖고 있다. API 가 닿는 가장 오래된 경기는
대략 **2026-08-04**(DB 기준 최신에서 3,024번째)이니, **한 달 남짓 지난 경기는 API 에서
사라진다.**

> **결론은 맞았고 근거의 규모가 틀렸다.** "하루만 걸러도 뚫린다"가 아니라 "한 달쯤
> 지나면 사라진다"였다. 누적 저장은 여전히 옳은 결정이다.
>
> 이게 이 건이 오래 살아남은 이유이기도 하다. **틀린 근거가 옳은 결론을 떠받치고
> 있으면, 결론이 잘 작동하는 한 근거를 다시 보지 않는다.** DB 는 잘 쌓이고 있었고
> 화면도 잘 나왔다. 아무것도 깨지지 않았다.

## 왜 이런 일이 일어나나

정정이 어디에 남았는지를 보면 답이 나온다.

| | 정정이 갔나 |
|---|---|
| 커밋 메시지 (`d872ef5`) | ✅ 정확하게 |
| 코드 (`nexon_api.py` 의 `offset`) | ✅ 그날 |
| README | ❌ |
| `CLAUDE.md` | ❌ (오히려 나중에 새로 들어감) |

**커밋 메시지는 그 순간의 나에게 쓰는 글이고, 문서는 나중의 나에게 쓰는 글이다.**
정정은 앞쪽에만 남았다. 그리고 나중에 문서를 쓸 때 참고한 것은 **커밋 메시지가 아니라
이전 문서**였다.

전역 규칙에 *"커밋 메시지는 왜를 남긴다"* 가 있다. 이 저장소는 그걸 잘 지켜서
커밋 본문이 658줄이고 문서(512줄)보다 두껍다. **그런데 그 규칙만으로는 이 실패를
못 막는다** — `git log` 에 남은 정정은 문서를 옮겨 적는 사람에게 자동으로 닿지 않는다.

## 같은 저장소에 두 번째 사례가 있다

`CLAUDE.md` 의 "나중에 (필요가 생기면 도입)" 표가 있다. 일부러 안 만든 것들과 그
도입 조건을 적어 두는 자리다.

08-04 에 다른 작업을 하다 그 표를 보니 **4개 중 3개가 이미 도입돼 있었다** —
회귀 테스트, SQLite 누적 저장, exe 빌드. 전부 "❌ 아직"으로 적힌 채였다.

`ddcc837`

이쪽은 방치형이라 더 흔한 종류다. 하지만 뿌리는 같다 — **문서는 상태를 복제하고,
복제본은 원본이 바뀔 때 같이 안 바뀐다.**

## 반대 방향의 사례도 하나 있다

같은 저장소에서 이건 잘했다. 카카오톡 봇 어댑터 연결 문서를 쓰면서, 에뮬레이터
주소를 이렇게 적었다.

> 에뮬레이터 주소는 **AVD만 `10.0.2.2` 로 단언**하고 LDPlayer·녹스는 *"먼저 시도하고
> 안 되면 PC 내부 IP"* 로 적었다 — **확인하지 않은 것을 단언하지 않기 위해서다.**

`68196b0`

AVD 는 실제로 확인했고 나머지 둘은 확인하지 못했다. 그 차이를 문장 형태로 남겼다.
**"확인했다"와 "아마 그럴 것이다"가 문서에서 같은 모양이 되면, 나중에 어느 쪽이었는지
알 수 없게 된다** — 이번 건이 정확히 그 상태였다. `462b1e7` 의 "100경기까지만"은
확인한 것처럼 적혀 있었지만 실제로는 첫 응답을 보고 추측한 것이었다.

## 고쳤다

이 노트를 쓰기 전에 문서를 먼저 고쳤다. 노트가 *"지금도 틀려 있다"* 고 적는 순간
그 문장이 다시 낡기 때문이다.

`0e6e19f` — README 세 곳과 `CLAUDE.md` 한 곳. 고칠 때 셋을 지켰다.

1. **결론은 두고 근거를 갈았다.** 누적 저장이 필요하다는 결론은 맞았으므로 그대로
   두고, "100경기" 대신 실측(3,024 vs 7,859)을 넣었다.
2. **실측 명령과 날짜를 같이 적었다.** 다음에 이 문장이 의심스러우면 그대로 다시
   돌려 보면 된다.
3. **틀렸던 문장을 지우지 않고 ⚠️ 로 남겼다.** 지우면 다음에 같은 값을 다시 적게
   된다 — 이번 일이 바로 그것이었다.

## 이 건에서 남긴 규칙

**정정은 커밋 메시지로 끝나지 않는다. 그 사실을 주장하는 문서를 같이 고친다.**
`git log` 는 그 순간의 기록이고 문서는 다음 사람이 읽는 것이다. 둘 사이에 자동
연결은 없다.

그리고 문서를 새로 쓸 때 **기존 서술을 옮겨 적는 것은 새로 주장하는 것과 같다.**
옮기기 전에 그 문장이 아직 참인지 묻는 단계가 있어야 한다. 이번에는 그 단계가 없어서,
반증된 문장이 6일 만에 더 눈에 띄는 자리(README 첫 화면)로 승격됐다.

**확인한 것과 추측한 것을 문서에서 구분해 적으면** 이 질문이 훨씬 싸진다. "실측
(날짜)" 라고 붙어 있으면 다시 잴 수 있고, 안 붙어 있으면 의심할 이유가 된다.
