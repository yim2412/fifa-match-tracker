# 개발 노트 — 피파 전적관리

만들면서 **무엇이 어떻게 깨졌고 어떻게 알아냈는지**의 기록이다. 기능 소개가 아니라
**판단 기록**이라 *"이건 아직 안 쟀다"* 도 그대로 적는다. 각 노트 끝의 **근거** 에서
커밋과 실측 명령을 확인할 수 있다.

앱이다. 계산은 어렵지 않은 앱이라, 실제로 틀린 것도 계산이 아닌 쪽에서 나왔다.

## 두 편인 이유

후보를 캐는 단계에서 **40건**이 나왔다. 그중 **한 편을 지탱할 만큼 서사가 이어지는
것이 둘**이라 둘만 썼다. 나머지는 좋은 한 문단이지 한 편이 아니다 —
[`CANDIDATES.md`](CANDIDATES.md) 에 전부 있고, **왜 안 골랐는지**도 적어 뒀다.

억지로 채우지 않은 이유는 하나다. 노트가 내건 것이 *"기능 자랑이 아니라 실패와 그
발견 과정"* 인데, 발견 과정이 한 줄인 것을 한 편으로 늘리면 그 자리를 다른 말로
메우게 된다.

**다음 순번으로 올려 둔 것 셋:**

1. **공개 저장소에 실제 계정 정보를 올렸다** — 테스트 픽스처가 실응답 그대로라
   `ouid`(영구 식별자)·`matchId`(하나만 있어도 참가자를 조회할 수 있다)·**제3자
   구단주명 4개**가 노출돼 있었다. 파일명까지 고쳐야 했고, 반대로 골·좌표는 일부러
   원본으로 뒀다 — 골든 테스트의 의미가 거기 있기 때문이다. 단독으로는 가장 강한데
   **발견 경로가 한 줄**이라 미뤘다
2. **검사 도구가 실행 환경과 달라 아무것도 안 잡았다** — 메신저봇R 은 Rhino(ES5)인데
   `node` 로 문법을 검사하면 최신 문법을 전부 통과시킨다. 폰에 올린 뒤에야 안다
3. **혼자 쓰는 전제로 만든 것이 여러 명이 쓰자 전부 틀렸다** — 오픈채팅 봇에서
   "마지막으로 조회한 계정"이 옆 사람 것을 보고, 방 단위 쿨다운이 남을 막았다

## 이 저장소의 특이점 — 주 재료가 문서가 아니었다

노트를 캘 때 보통은 정리된 문서를 먼저 훑고 `git log` 는 근거 조회용으로 쓴다.
**여기서는 뒤집힌다.**

```
문서        512줄   (CLAUDE.md 127 · README.md 275 · adapters/README.md 110)
커밋 본문   658줄   (커밋 77개)
```

전역 규칙이 *"커밋 메시지는 왜를 남긴다"* 를 요구한 덕에 `git log` 가 문서보다
두껍다. 그런데 **노트 01 이 정확히 그 비대칭에서 나온 실패다** — 정정이 커밋
메시지에만 남고 문서에는 가지 않았다.
