# 중앙 조회 서버 (서비스 키) — 설계·구현 지침

> **중앙 서버 계획의 정본은 이 문서 하나**(2026-10-19 바탕화면에서 옮김). `docs/ROADMAP.md` 의 "중앙 조회 서버" 절은 여기를 가리키기만 한다. 작업 전에 `CLAUDE.md` 를 먼저 읽는다.
> 이 문서의 **"확인됨"** 은 근거가 있는 것, **"미확인"** 은 사람이 먼저 확인해야 하는 것이다. 미확인을 추측으로 메우지 않는다.

## 1. 목적

지금은 사용자 PC 마다 자기 넥슨 키로 같은 공개 데이터를 따로 받는다(랭킹 1만 명 수집 · 랭커 픽 하루 300요청 · 포지션 특성 · 구단주 분포 한 바퀴 약 15만 요청). 개발 단계 키는 하루 1,000건이라 첫 조회(한 달 치 최대 3천 경기 이상)도 끝내지 못한다.

**서비스 키 하나를 서버가 들고 대신 조회·캐시·수집하고, 앱은 서버 주소만 쓴다.**

- 확인됨: 넥슨 FAQ 기준 서비스 단계 한도는 **초당 500건 · 하루 2,000만 건**(개발 단계 초당 5 · 하루 1,000). 출처: https://openapi.nexon.com/ko/support/faq/2354215/
- 하루 15만 요청짜리 구단주 분포 한 바퀴는 일일 한도의 1% 미만이다. 사용자 수와 무관하게 서버가 한 번만 돈다.

## 2. 착수 게이트 — 사람이 먼저 확인

코드를 로컬에서 짜는 것은 괜찮지만 **공개 배포는 아래가 끝나기 전엔 하지 않는다.**

| # | 확인할 것 | 어디서 | 상태 |
|---|---|---|---|
| G1 | 서비스 단계 등록 조건(서비스 URL · 이미지 · 심사). 취미 무료 서비스도 승인되나 | 넥슨 오픈API 포털 "사전 준비하기" | **가능 — 사용자 확인(2026-10-19)** |
| G2 | 약관상 응답 데이터 저장·재배포 범위(서버가 다른 사람의 경기를 쌓는 것 · 집계본 공개) | 오픈API 이용약관 | **가능 — 사용자 확인(2026-10-19)** |
| G3 | **같은 계정의 `ouid` 가 키(애플리케이션)가 달라도 같은 값인가.** 다르면 사용자 로컬 DB 의 기존 `ouid` 와 서버 모드 `ouid` 가 어긋나 기록이 끊긴다 | 키 두 개로 `/fconline/v1/id` 를 같은 닉네임에 호출해 비교 | **확인됨(2026-10-19)** — 앱 키·서비스 키로 랭커 5명(1·2,500·5,000·7,500·10,000위 근처) 전부 같음. 두 키 모두 같은 개발자 계정 것이라 "남이 발급한 키" 까지는 안 쟀다 |
| G4 | 개인정보 처리 안내(닉네임·식별자 보관 기간·삭제 요청 방법) — 서비스 등록에도 필요할 가능성 | 직접 작성 | 미작성 |
| G5 | 넥슨 홈페이지(데이터센터) 약관상 **자동 수집한 것을 서버가 모아 남에게 나눠 주는 것**이 되나(3절 — 홈페이지 값도 서버로) | 넥슨 홈페이지 이용약관 | **가능 — 사용자 확인(2026-10-19)** |

G1·G2·G5 는 사용자가 확인했다(근거 조항·답변은 이 문서에 아직 없다 — 이용 안내(4·6절)를 고칠 때 인용할 수 있게 받아 둔다). 남은 관문은 G4(안내 작성)뿐이고, 공개(1단계 ⓑ) 전에 끝낸다.

## 3. 범위

### 서버가 대신하는 것 (오픈API, 서비스 키)

`nexon_api.py` 상수 기준:

| 상수 | 경로 | 서버 처리 |
|---|---|---|
| `EP_ID` | `/fconline/v1/id` | 닉네임 → ouid 짧은 캐시 |
| `EP_USER_BASIC` | `/fconline/v1/user/basic` | 짧은 캐시 |
| `EP_MAX_DIVISION` | `/fconline/v1/user/maxdivision` | 짧은 캐시 |
| `EP_USER_MATCH` | `/fconline/v1/user/match` | 짧은 캐시(새 경기 확인용이라 TTL 짧게) |
| `EP_MATCH_DETAIL` | `/fconline/v1/match-detail` | **영구 캐시** — 끝난 경기 상세는 안 변한다 |
| `EP_RANKER_STATS` | `/fconline/v1/ranker-stats` | 하루 캐시 |
| `META_URL` | `/static/fconline/meta` | 정적 메타, 긴 캐시 |

### 서버가 대신하지 않는 것

- **`EP_USER_TRADE` (거래)**: 넥슨은 ouid 를 무시하고 **키 주인의 거래만** 준다(CLAUDE.md "tradecollect"). 서버가 프록시하면 서비스 키 주인(운영자)의 거래가 모든 사용자에게 나간다. **절대 프록시하지 않는다.** 서버 모드에선 가계부·타임라인 거래 부분을 "내 키를 넣으면 보임"으로 안내하거나 사용자 키 직접 호출 경로를 남긴다.
### 넥슨 홈페이지 값 — 서버로 (2026-10-19 사용자 결정 · G5 조건)

`ranker.py`·`teamcolor.py`·`playerinfo.py`·`seasons.py`·`traitcollect.py`·`cardcollect.py`·`predict_check.py` 의 홈페이지 요청도 서버가 맡는다.
처음 안은 "서버는 오픈API 만"이었다 — 서버 IP 하나가 막히면 전원이 멈추고 재배포 약관이 새로 걸리기 때문. 뒤집은 이유:
**넥슨이 받는 요청이 사용자 수에 비례하지 않게 된다**(랭킹 500쪽을 수집을 켠 사용자마다 → 서버 하루 한 번) · 카드·시즌표·팀컬러 표는
거의 안 변해 공유 캐시가 크게 먹힌다 · 토글을 안 켠 사용자도 구단가치·FC 등수를 본다.
- 요청 규칙은 지금 그대로: `config.WEB_USER_AGENT`(앱 이름) · `ranker.web_get` 동시 상한 · 막히면 쉼 · 같은 내용은 캐시.
- 상대마다 순위 검색(`fetch_manager_rank`)은 사용자 수에 비례하는 유일한 홈페이지 요청이다 — 서버 쪽 하루 상한을 따로 둔다.
- 서버가 막히거나 꺼지면 웹 데이터를 켠 사용자만 지금처럼 자기 PC 에서 직접(폴백).
- 시기는 5절 2단계(수집 이전)와 같이. 1단계는 이 결정과 무관하게 먼저 간다.

## 4. 아키텍처

```
앱(PyQt6) ──HTTPS──> Cloudflare(프록시·캐시·보호) ──> 서버(FastAPI) ──서비스 키──> 넥슨 오픈API
   │                                                      │
   └ 로컬 SQLite(fifa.db) 개인 누적은 그대로               └ 공유 캐시 DB + 수집기(cron)
```

- 개인 전적 누적(`fifa.db`)은 **로컬 유지.** 서버는 공유 캐시와 공개 집계만 둔다.
- 서버 스택(권장): **Oracle Cloud Always Free VM + FastAPI + SQLite(WAL) 또는 Postgres**, 앞단에 Cloudflare. 기존 수집기(`rankcollect.py`·`ownerdist.py`·`rankerpick.py`)가 파이썬이라 거의 그대로 올린다. 무료 한도·정책(ARM 재고 부족, 유휴 인스턴스 회수)은 **미확인** — 가입 전에 직접 확인.

### 서버 자리 (2026-10-19 조사 — 숫자는 대부분 블로그·보도라 가입 전에 공식 문서로 다시)

| 후보 | 판정 | 근거 |
|---|---|---|
| **GitHub**(Actions·Pages·저장소) | ✖ | Actions 약관 금지 용도에 *"don't use Actions as a content delivery network or as part of a serverless application"* · *"activity unrelated to the production, testing, deployment, or publication of the software project"*. Pages 는 정적 파일만 · 공개 저장소면 남의 닉네임·전적이 공개. **계정이 정지되면 릴리스·자동 업데이트(`updatecheck.py`)까지 같이 죽는다** — 배포 계정을 서버로 쓰지 않는다 |
| **이 PC + 무료 터널** | 1단계 **시험용** | 돈·가입 없음 · 가정용 한국 IP(차단 위험이 가장 낮다고 봄 — 미측정) · 꺼지면 전원 폴백. **사용자가 게임 중일 때는 띄우지 않는다** — 부하는 시험 때 잰다 |
| **Oracle Cloud Always Free(서울 리전)** | 1~3단계 **본 서버 후보** | VM 한 대 · 블록 저장 200GB. 2026년에 A1 무료 몫이 4코어·24GB → 2코어·12GB 로 줄었다는 보도(날짜가 출처마다 다름) · 유휴 회수 규칙(2023 기준 7일간 CPU·네트워크·메모리 15% 미만) · 카드 등록 필요 · 해외 클라우드 IP 를 넥슨이 막는지는 모른다 |
| Cloudflare Workers + R2 | 1단계만 · 예비안 | 하루 10만 요청 · R2 10GB · 요청당 CPU 약 30ms — 큰 수집은 못 한다 · 파이썬 코드를 JS 로 다시 짜야 한다 |

순서: 이 PC 에서 1단계 시험(넥슨 반응·속도·부하를 잰다) → 되면 Oracle 로 옮긴다 → Oracle 이 막히면 Cloudflare 에 1단계만.
- 서버 코드는 `server/` 폴더(또는 별도 저장소). **PyInstaller spec·`tools/release.py` 개인정보 검사 대상에서 서버 코드와 키가 새어 들어가지 않는지** 확인한다.

## 5. 단계별 작업

### 1단계 — 프록시 + 공유 캐시 (먼저, 이것만으로도 가치가 있다)

- FastAPI 서버: 3절 표의 엔드포인트를 **허용 목록**으로만 중계(임의 경로 중계 금지 — SSRF 방지).
- 경기 상세는 `match_id` 키로 영구 저장, 이후 요청은 넥슨을 부르지 않는다.
- 넥슨 오류(`OPENAPI00007` 429 등)는 `nexon_api.ERROR_MESSAGES` 의 코드 체계 그대로 앱에 돌려줘서 앱의 기존 오류 처리가 그대로 동작하게 한다.
- 서비스 키는 환경 변수로만. 로그·응답·오류 메시지에 키가 찍히면 안 된다.
- **완료 기준**: 가짜 넥슨 서버로 서버 단위 테스트(캐시 적중 시 업스트림 호출 0 · 429 전달 · 허용 목록 밖 경로 거절 · 키가 응답에 없음).

### 2단계 — 수집기를 서버로 이전

- `rankcollect.py`(랭킹 1만 명 · 하루 1회) · `ownerdist.py`(구단주 분포 바퀴) · `rankerpick.py`·`traitcollect.py` 를 서버 cron 으로.
- 서버 수집은 기존 앱 규칙(하루 계수 · 429 쉼 · 재시도 끔)을 **서비스 한도에 맞춰** 가져오되, 한도 여유분을 사용자 프록시 호출용으로 **예약**한다(수집이 사용자 조회를 굶기지 않게).
- 원본 보관은 기존 정책(원본 14일, 집계는 영구, 닉네임 없는 요약)을 유지한다. ROADMAP "하지 않기로 한 것"의 "남의 원본을 계속 저장" 결정(2026-10-19)을 어기지 않는다.
  단 **경기 상세는 서버에 영구 보관**한다(2026-10-19 사용자 · 9절 6) — "남의 원본 계속 저장 안 함" 은 사용자 PC 이야기로 남고, 서버의 경기 상세만 예외다.
  랭킹 원본(닉네임·점수 스냅숏)은 지금처럼 14일.
- **완료 기준**: 서버 1회 수집 결과가 기존 로컬 수집과 같은 집계 값을 낸다(골든 비교).

### 3단계 — 집계 읽기 API

- 앱이 `rankmeta.py` 류 화면에 쓸 집계(컷 ELO · 팀컬러·포메이션 비율 · 구단주 분포 요약 · 랭커 픽)를 읽기 전용으로 내려준다. 닉네임 없는 값만.
- 앱은 자기 PC 수집 대신 이걸 받는다. 로컬 수집 코드는 폴백으로 남긴다.

## 6. 클라이언트(앱) 변경

`nexon_api.py` 에 `BASE_URL` 하나와 `FCOnlineAPI._get`(요청 한 곳)·`x-nxopen-api-key` 헤더 설정이 모여 있어 변경 지점이 작다.

- 새 설정 `FIFA_SERVER_URL`(`.env`). 값이 있으면 서버 모드: `BASE_URL` 을 서버로 바꾸고 `x-nxopen-api-key` 대신 익명 설치 ID 헤더를 보낸다. 값이 없으면 지금과 똑같이 동작한다.
- **폴백 유지**: 서버가 죽거나 응답이 없으면(연속 실패 N회) 사용자가 키를 넣어 둔 경우 직접 호출로 되돌린다. 서버 단일 장애로 전원이 멈추지 않게.
- 첫 실행 `ApiKeyDialog`·`check_key`: 서버 모드에선 키 입력을 필수에서 선택(거래 기능용)으로 바꾼다.
- 거래 기능(`tradecollect.py`)은 3절대로 사용자 키가 있을 때만.
- `from config import API_KEY` 금지(CLAUDE.md) — 모듈 경유로 읽는다.
- 이용 안내(`notice.py`)와 README 의 **"서버 없음 · 개발자 서버 없음"** 문구를 고치고 **`config.NOTICE_VERSION` 을 올려** 재동의를 받는다(`test_notice_text_bumps_version` 이 짝을 지킨다). 서버가 받는 정보(닉네임 조회 · 설치 ID · IP)와 보관 기간을 적는다.
- 테스트: 가짜 서버로 서버 모드·폴백 전환·키 없는 서버 모드를 `tests/` 에 추가. 새 테스트의 `main()` 은 `watchdog.limit` 안에서, 네트워크 없이.

## 7. 보안·남용 방지

- 키가 하나라 한 사용자가 한도를 태우면 전원이 막힌다. 서버에서 **설치 ID · IP 별 호출 상한**과 전체 한도의 **일일 예산 + 예약분**을 둔다. exe 에 넣은 비밀값은 역컴파일로 나오므로 인증 수단으로 쓰지 않는다 — 익명 ID + 상한으로 막는다.
- 입력 검증: 닉네임 길이·문자, `match_id` 형식, 숫자 범위를 서버에서 검사.
- 서버 오류 응답은 사람 말(한국어)로, 내부 정보 없이.
- 상태 확인용 `/health`, 서버 로그에는 닉네임 대신 해시 사용, 로그 보관 기간 제한.

## 8. 데이터·개인정보

- 서버가 쌓는 것: 경기 상세 캐시 · 닉네임→ouid 짧은 캐시 · 닉네임 없는 집계. 보관 기간을 정해 지우는 작업을 cron 에 둔다(원본 14일 원칙).
- 삭제 요청 길(닉네임 기준 지우기)을 둔다 — G4 와 함께 결정.
- 오래 보관하는 본인용 수집(`tools/dev_archive.py`)은 서버와 분리한 채 둔다.

6. ~~서버의 경기 상세 보관 기간~~ → **영구**(2026-10-19 사용자 · 추천은 14일이었다). 결과: 랭커 수집까지 서버로 오면(2단계) 하루 약 0.6~0.75GB 가
   쌓여 Oracle 200GB 는 약 9~11달이면 찬다(계산값 — 실측 상세 2.5KB × 하루 24만~30만 경기). 그 전에 압축(상세 JSON 은 gzip 이 잘 먹는다 — 미측정)이나
   오래된 것 정리를 다시 정한다. 삭제 요청 길(8절)은 영구 보관이라 더 필요하다. 아래는 기각한 비교 — 영구(캐시 효과 최대 · 10-19 "남의 원본 계속 저장 안 함" 은 **사용자 PC 마다** 쌓이는 위험 이야기였지만, 한 곳이라도 남의 경기가 무기한 쌓이는 건 같다) vs 14일(원칙 유지 · 14일 지난 경기는 넥슨에 다시 묻는다). 1단계 설계 전에 정한다.

## 11. 1단계 설계 1판 (2026-10-19 — 계획 검토 전 초안)

**한 줄**: 서버는 넥슨 오픈API 경로를 **같은 모양 그대로** 받아 대신 묻고 저장한다. 앱은 `BASE_URL` 과 헤더만 바꾼다 — 응답·오류 모양이 같아서
앱의 파싱·오류 처리(`_parse_error`·`ERROR_MESSAGES`·429 재시도)는 한 줄도 안 바뀐다.

1단계를 둘로 나눈다 — **사용자에게 보이는 변화가 생기는 순간이 공개**라서.

| 조각 | 내용 | 공개 | 난이도 |
|---|---|---|---|
| **ⓐ 서버 + 숨은 스위치** | `server/` · 앱은 `.env` 에 `FIFA_SERVER_URL` 이 있을 때만 서버로(화면·안내 변화 0) · 이 PC + 터널로 사용자 본인만 시험 · 실측 | 없음 | 중간 |
| **ⓑ 화면·안내·공개** | 첫 실행 키 입력을 선택으로 · 거래 안내 · 이용 안내(G4 — 서버가 받는 것·보관 기간·삭제 요청) `NOTICE_VERSION` 올림 · 서버를 Oracle 로 · 이때 단계 번호를 받는다 | 앱 공개 | 중간 |

### 서버 (`server/` — 이 저장소 · 9절 5 의 추천)
같은 저장소에 두는 이유: 경로 상수(`nexon_api.EP_*`)를 서버가 **import 해서** 허용 목록을 만든다 — 두 벌이면 넥슨 경로가 바뀔 때 한쪽만 고친다.
exe 에는 안 들어간다(spec 진입점이 `app_main.py` 라 import 안 되는 것은 안 실린다 — `tools/release.py` 검사에 "`server/` 가 번들에 없음" 한 줄 추가).

| 파일 | 역할 |
|---|---|
| `server/app.py` | FastAPI — 허용 목록 경로만 · 그 밖은 404(임의 경로 중계 금지) · `/health` |
| `server/upstream.py` | 넥슨 요청 한 곳 — 서비스 키(환경 변수 `NEXON_SERVICE_KEY`만) · 동시 상한 · 하루 계수 |
| `server/cache.py` | SQLite(WAL) — 표 `detail`(match_id PK · gzip 본문 · 받은 시각 · **영구**) · `short`(경로+인자 키 · 본문 · 만료 시각) |
| `server/limits.py` | 설치 ID·IP 별 상한(토큰 버킷) · 전체 하루 예산 |
| `server/settings.py` | 상수 전부(전역 규칙 6) — TTL·상한·포트 |
| `server/tests/test_server.py` | 가짜 넥슨으로 — 아래 "완료 기준" |

경로별 처리(`settings.py` 의 TTL — 시작값, 시험에서 잰 뒤 고친다):

| 경로 | 저장 | 이유 |
|---|---|---|
| `match-detail` | **영구**(9절 6) | 끝난 경기는 안 변한다 · 오류 응답은 저장 안 함 |
| `id` | 10분 | 닉네임 변경이 드물지만 바뀌면 남의 ouid 를 줄 수 있어 짧게 |
| `user/match` | 60초 | 새 경기 확인용 — 길면 방금 한 경기가 안 보인다 |
| `user/basic` · `user/maxdivision` | 1시간 | 등급은 경기 뒤 바뀐다 |
| `ranker-stats` | 하루 | 앱도 하루 캐시(`ranker_stats`) |
| `static/fconline/meta/*.json` | 금요일 기준(앱의 `META_REFRESH_WEEKDAY` 와 같은 규칙) | 이름 목록은 허용 목록으로 |
| `user/trade` | **허용 목록에 없다** | 키 주인 거래만 준다 — 운영자 거래가 전원에게 나간다(3절) |

- **오류는 넥슨 것을 그대로**: 상태 코드 + `{"error":{"name","message"}}` 본문. 서버 자체 거절(상한 초과)은 429 + `OPENAPI00007` 로 — 앱이 이미 아는 신호라 물러난다.
  서버 고장은 502/503(앱은 5xx 를 재시도 후 폴백).
- **같은 경기를 동시에 물으면 넥슨에는 한 번만**(경기 id 별 잠금) — 두 사용자가 같은 경기를 동시에 여는 경우가 흔하다(서로의 상대).
- **키는 어디에도 안 찍힌다**: 로그·응답·오류 본문. 로그는 닉네임 대신 해시(7절).
- 이 PC 시험: `127.0.0.1` 에만 묶고 Cloudflare 무료 터널(`cloudflared`)로 바깥 주소를 낸다 — 공유기 포트를 안 연다.
  **게임 중엔 안 띄운다.** 띄우는 명령은 `bgrun.js` 로 감싸 상태줄에 보이게.
